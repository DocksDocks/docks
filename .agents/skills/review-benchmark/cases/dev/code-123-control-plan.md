## Goal

Add two docks skills under `plugins/docks/skills/engineering/`:

1. `ci-speed`: helps an agent measure and cut the wall time of continuous integration (CI) and test runs, with GitHub Actions as the main target. It covers queue time and runner choice, checkout, installs and caches, lint, format, and type-check tools, test parallelism, isolation, and sharding, job graphs and affected-only runs, and local pre-push checks. Guidance for the Blacksmith runner service ships as references inside this skill, together with one workflow setup that runs on Blacksmith and falls back to GitHub-hosted runners when the Blacksmith budget or service is not available.
2. `effect-ts`: helps an agent write, test, and check TypeScript code that uses Effect v4: services, layers, typed errors, `@effect/vitest` tests, the Effect language-service diagnostics as lint rules in the editor, the agent loop, and CI, and rules that keep agents on the installed Effect version instead of names that do not exist in v4. The user uses Effect v4 only, so the skill carries no v3 migration content.

Scope: the two skill folders, the skill tables in `README.md` and `plugins/docks/README.md`, and the skill metadata that the repository tooling writes. No version bump: the release flow owns it.

Yolo: the user delegated every decision except the merge to the agent.

Mode: plan-and-implement

### Request corrections

- Asked: "Blobless clones". Did: keep the default `fetch-depth: 1` for jobs that need no history, and use `fetch-depth: 0` with `filter: blob:none` or `filter: tree:0` only for jobs that need history. Reason: `filter` does not change the default depth of 1, so a filter alone is still a shallow clone (https://github.com/actions/checkout README; https://github.blog/open-source/git/get-up-to-speed-with-partial-clone-and-shallow-clone/; Nx uses `tree:0`, https://nx.dev/docs/features/ci-features/affected).
- Asked: "Vitest isolation off". Did: turn off isolation only for a separate Vitest project of proven files, and prove it with `vitest doctor`, the same test count, and repeated shuffled runs. Reason: `isolate: false` shares module state between files, and `restoreMocks` still defaults to false (https://vitest.dev/config/isolate, https://vitest.dev/guide/improving-performance, https://vitest.dev/config/restoremocks).
- Asked: "Bigger test machines". Did: size runners from the measured phase that uses the CPU. Reason: Playwright recommends `workers: 1` plus sharding in CI (https://playwright.dev/docs/ci), and Vitest names the main Vite server as a bottleneck on machines with many cores (https://vitest.dev/guide/improving-performance).
- Asked: "bun check for tsc". Did: TypeScript 7 `tsc` stays the default type checker, and `bun check` is the faster option for Bun projects with its limits named. Reason: `bun check` exists since Bun 1.4.3, writes no `.tsbuildinfo`, emits no declarations, ignores `compilerOptions.plugins`, and runs a `check` script from `package.json` if one exists (https://bun.com/docs/runtime/check, https://bun.sh/blog/bun-v1.4.3).
- Asked: "ubuntu-slim" for CI jobs (the user later said it is not mandatory). Did: `ubuntu-slim` only for gate, picker, change-detection, and format jobs well under 15 minutes. Reason: 1 vCPU, 5 GB RAM, an unprivileged container without Docker-in-Docker, and a 15-minute job limit (https://docs.github.com/en/actions/reference/runners/github-hosted-runners, section "Single-CPU runners").
- Asked: "the Effect language service lint rules" on TypeScript 7 and Bun. Did: `@effect/tsgo` (binary `effect-tsgo`). Reason: the `@effect/language-service` README says to use `@effect/tsgo` on TypeScript 7 (https://github.com/Effect-TS/language-service), and `bun check` ignores compiler plugins, so it never reports Effect diagnostics (https://bun.com/docs/runtime/check; experiment below).
- Asked: "effect 4.1.2, which currently is the latest". Did: the skill names no live Effect version. It tells the agent to read the installed version and the guide that ships in the package. Reason: durable-docs rule C, and Effect unstable modules can break in minor releases (https://github.com/Effect-TS/effect/blob/main/MIGRATION.md, "Unstable Module System").
- Asked: "i only use effect v4 so not necessary the v3 information". Did: no v3-to-v4 reference file, no migration workflow, and no migration trigger in the description. The skill keeps one short table of names that agents write from memory but that do not exist in Effect 4, with their v4 names, and routes an Effect 3 project to the official `effect-v3-to-v4` skill (https://github.com/Effect-TS/skills). Reason: agents write v3 and beta names in v4 code (research failure modes; the `outdatedApi` diagnostic exists for this, https://github.com/Effect-TS/tsgo), so the table guards v4 code and is not migration content.

### Decisions

- D1. Blacksmith guidance is two references inside `ci-speed` (`references/blacksmith.md`, `references/runner-fallback.md`), not a second skill. Evidence: runner choice is one lever of CI speed, and a separate skill would share most trigger words with `ci-speed`, which `tests/skill-trigger-collision.mjs` flags. Rejected: a separate `blacksmith` skill.
- D2. One workflow for Blacksmith and GitHub-hosted runners. GitHub has no runner fallback: a label list must match all labels, and a job with no matching runner stays queued, up to 24 hours for self-hosted runners (https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax#jobsjob_idruns-on, https://docs.github.com/en/actions/reference/runners/self-hosted-runners). Blacksmith has no hard spend cap; Spending Alerts only send email (https://docs.blacksmith.sh/introduction/settings), and it can suspend an account that is behind on payment (https://docs.blacksmith.sh/about/terms-of-service). The design:
  - Each runner class reads one configuration variable with a literal GitHub-hosted fallback: `runs-on: ${{ vars.CI_RUNNER_LINUX || 'ubuntu-latest' }}`. `runs-on` accepts the `vars`, `needs`, `inputs`, and `matrix` contexts (https://docs.github.com/en/actions/reference/workflows-and-actions/contexts#context-availability). An unset variable is an empty string, so the fallback applies.
  - The literal fallback is required: GitHub does not pass configuration variables to `pull_request` runs from forks, and an empty `runs-on` fails (https://github.com/orgs/community/discussions/44322). Fork runs then use GitHub-hosted runners, which also keeps untrusted fork code off the Blacksmith bill. Correction (found by the second baseline grading): Dependabot-triggered runs do get Actions variables (GitHub staff reply of 2023-03-13 in https://github.com/orgs/community/discussions/44088), so Dependabot runs follow the variable like other same-repository runs.
  - Manual switch: `gh variable set` or `gh variable delete` (https://cli.github.com/manual/gh_variable_set). A repository variable overrides an organization variable (https://docs.github.com/en/actions/reference/workflows-and-actions/variables#configuration-variable-precedence).
  - Optional automatic switch: a picker job on a GitHub-hosted runner reads a force variable and the Blacksmith status page `https://status.blacksmith.sh/summary.json` (Instatus public data, https://instatus.com/help/api/public-data). It holds no secret, and it always picks a GitHub-hosted label for fork pull requests, as Pattern 1 does. The aggregate required job lists the picker in `needs`, so a failed picker fails the required check.
  - Optional scheduled guard (changed in code review round 1): one scheduled workflow on a GitHub-hosted runner does two checks. It compares the month-to-date `blacksmith usage` cost (https://docs.blacksmith.sh/blacksmith-cli/usage) with a budget variable, and it lists jobs queued on `blacksmith-` labels (https://docs.github.com/en/rest/actions/workflow-jobs). The Blacksmith org token is an environment secret that only the default branch can use, because the token can manage caches and sticky disks of every installed repository (https://docs.blacksmith.sh/blacksmith-cli/overview). `GITHUB_TOKEN` has no variables permission (https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax#permissions), so the guard mints a GitHub App token in the job with `actions/create-github-app-token`; installation tokens expire after 1 hour (https://github.com/actions/create-github-app-token). On a fallback, the guard sets `CI_FORCE_GITHUB=1` (the picker reads it) and switches the label variables to GitHub-hosted labels (Pattern 1 jobs read them). Both writes happen before it cancels the stuck runs (`actions: write`); then it re-runs them. Recovery clears `CI_FORCE_GITHUB` and resets the label variables. Rejected: the budget check inside the picker, because it put the org token in every pull request run.
  - Portable steps: upstream cache and setup actions work on both, because Blacksmith redirects `actions/cache` and `setup-*` caches to its own cache (https://docs.blacksmith.sh/blacksmith-caching/dependencies-actions). `useblacksmith/build-push-action` works only on Blacksmith (https://github.com/useblacksmith/build-push-action), so it needs a step condition and a `docker/build-push-action` twin. Blacksmith runners report `runner.environment == 'self-hosted'` (https://docs.github.com/en/actions/reference/workflows-and-actions/variables; third-party report https://github.com/cicd-sensor/cicd-sensor/issues/195), so `astral-sh/setup-uv` turns its automatic cache off there (https://github.com/astral-sh/setup-uv/blob/main/docs/caching.md). Docker Hub rate limits apply to self-hosted runners (https://docs.github.com/en/actions/reference/limits).
  - Rejected: a label array as a fallback list (AND semantics); a separate workflow file per runner (duplicated YAML that drifts).
- D3. Blacksmith facts the reference carries, each with its URL: label format `blacksmith-<N>vcpu-<os>-<version>[-arm]` (https://docs.blacksmith.sh/blacksmith-runners/overview); the GitHub App must be on every repository that uses the labels (same page, FAQ); the archived `useblacksmith/cache` and `useblacksmith/setup-*` forks (https://github.com/useblacksmith/cache); Docker builds through `useblacksmith/setup-docker-builder` with a required `cache-key` (https://docs.blacksmith.sh/blacksmith-caching/docker-builds); sticky-disk writes from pull requests unless Branch Protection is on (https://docs.blacksmith.sh/blacksmith-caching/dependencies-sticky-disks); observability and SSH (https://docs.blacksmith.sh/blacksmith-observability/ssh-access); prices only through https://www.blacksmith.sh/pricing. BuildJet shut down (https://buildjet.com/for-github-actions/blog/we-are-shutting-down) and is not listed among alternatives.
- D4. GitHub Actions facts for `ci-speed/references/github-actions.md`: queue seconds are `started_at - created_at` from `GET /repos/{owner}/{repo}/actions/runs/{run_id}/jobs`; `gh run view --json jobs` has no job `createdAt` (https://docs.github.com/en/rest/actions/workflow-jobs, https://cli.github.com/manual/gh_run_view). A cache saved by a pull request run is scoped to `refs/pull/N/merge`, so seed caches from `push` on the default branch (https://docs.github.com/en/actions/reference/workflows-and-actions/dependency-caching#restrictions-for-accessing-a-cache); `cache-mode` controls read and write per job (https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax#cache-mode). A workflow skipped by a path filter leaves a required check pending, and a job skipped by `if:` reports success (https://docs.github.com/en/pull-requests/how-tos/merge-and-close-pull-requests/troubleshooting-required-status-checks#handling-skipped-but-required-checks), so use one always-run aggregate job. In-job parallel steps exist (https://github.blog/changelog/2026-06-25-actions-steps-can-now-be-run-in-parallel/). Action majors change, so the skill gives a verify command (`gh release view --repo <owner>/<repo> --json tagName`) instead of trusting doc snippets, many of which pin old majors.
- D5. JavaScript toolchain facts for `ci-speed/references/js-toolchain.md`: oxlint with `@oxlint/migrate` and `eslint-plugin-oxlint` for a staged move off ESLint, type-aware rules through `oxlint-tsgolint` (https://oxc.rs/docs/guide/usage/linter/migrate-from-eslint.html, https://oxc.rs/docs/guide/usage/linter/type-aware.html); ESLint `--cache` does not track cross-file dependencies (https://eslint.org/docs/latest/use/command-line-interface). `bun fmt` exists since Bun 1.4.4, reads Prettier and oxfmt configuration, and has `--check` and `--no-script` (https://bun.com/docs/format, https://bun.com/blog/bun-v1.4.4). TypeScript 7 ships a native `tsc` with `--checkers`; `@typescript/native-preview` and `tsgo` are superseded (https://devblogs.microsoft.com/typescript/announcing-typescript-7-0/). pnpm 12 freezes the lockfile in CI by default, and its docs say not to use Corepack (https://pnpm.io/continuous-integration, https://pnpm.io/blog/whats-different-in-pnpm-12). Bun does not freeze the lockfile in CI by default; `bun ci` does (https://bun.com/docs/pm/cli/install). `oven-sh/setup-bun` caches only the Bun binary (https://github.com/oven-sh/setup-bun). A tool swap (ESLint to oxlint, Prettier to `bun fmt`) is proposed with its measured gain and made only on request, which matches `code-guardrails`.
- D6. Test-runner facts for `ci-speed/references/tests.md`: Vitest `isolate`, `pool`, `maxWorkers`, `--shard` with the blob reporter and `--merge-reports`, and `vitest doctor` (https://vitest.dev/guide/improving-performance, https://vitest.dev/guide/cli); `bun test --parallel`, `--shard`, and `--timings` (https://bun.com/docs/test/parallel); Playwright sharding, blob reports, and no browser caching (https://playwright.dev/docs/test-sharding, https://playwright.dev/docs/ci); Jest `--shard` (https://jestjs.io/docs/cli); pytest-xdist (https://pytest-xdist.readthedocs.io/en/stable/distribution.html), Go test caching (https://pkg.go.dev/cmd/go), cargo-nextest partitions (https://nexte.st/docs/ci-features/partitioning/).
- D7. Affected-only runs need the merge base: `nx affected` with `nrwl/nx-set-shas` (https://nx.dev/docs/features/ci-features/affected), Turborepo `--affected` (https://turborepo.com/docs/reference/run), pnpm `--filter "...[origin/main]"` (https://pnpm.io/filtering). The Turborepo docs suggest `--depth=0`, which git rejects; experiment below. Hooks give fast feedback and CI stays the gate, because `git push --no-verify` skips hooks (https://git-scm.com/docs/git-push); lefthook `parallel: true` (https://lefthook.dev/configuration/parallel).
- D8. Effect facts for `effect-ts`, checked against the `effect@4.1.2` tag (https://github.com/Effect-TS/effect): v4 lives on `Effect-TS/effect` `main`, and `effect-smol` is archived (https://github.com/Effect-TS/effect-smol). The npm package ships `AGENTS.md` (a copy of `LLMS.md`), `ai-docs/src`, and readable `src/**/*.ts` (https://unpkg.com/effect@4.1.2/package.json). The official skill tells agents to read `node_modules/effect/AGENTS.md` first (https://github.com/Effect-TS/skills, MIT). The rename map `migration/v3-to-v4.md` is about 17,000 lines and must be searched, not read whole (https://github.com/Effect-TS/skills/blob/main/skills/effect-v3-to-v4/SKILL.md). `effect/unstable/*` paths were removed in 4.0, `ServiceMap` became `Context`, and `Schema.TaggedErrorClass` became `Schema.TaggedError` again (https://github.com/Effect-TS/effect/blob/main/packages/effect/CHANGELOG.md). `@effect/vitest` has `it.effect`, `it.live`, `layer(...)`, and `it.effect.prop`, has no `it.scoped`, and needs Vitest 5 (https://github.com/Effect-TS/effect/blob/main/packages/vitest/README.md). The skill points at the shipped guide and source instead of copying API text, and adds what the official skill lacks: the `@effect/tsgo` check, the test gate, an old-name table, and an `AGENTS.md` block. `effect-mcp` and `effect-solutions` teach v3 or beta names, so the skill names them as sources to avoid (https://github.com/tim-smart/effect-mcp, https://github.com/kitlangton/effect-solutions).
- D9. Effect lint setup: `effect-tsgo tsc` gives one type-check pass with TypeScript and Effect diagnostics, and `effect-tsgo diagnostics --format github-actions --strict` gives pull request annotations (https://github.com/Effect-TS/tsgo#lsp-based-linter). ### Experiments

Scratch directory: `$(git rev-parse --git-path docks-review)/yolo-123/`.

- `git clone --filter=blob:none --depth=0 <repo>` with git 2.53.0 printed `fatal: depth 0 is not a positive number` (ToolingDocs research agent).
- `@effect/tsgo` 0.64.1, `typescript` 7.0.2, `effect` 4.1.2 (EffectLint research agent, in a removed scratch project): `effect-tsgo diagnostics --format text` exited 1 on an error-level finding and 0 on warnings only; `--strict` failed on warnings; `effect-tsgo tsc` failed on errors and warnings. `bun check` exited 0 on a file with an Effect warning, before and after `effect-tsgo patch`. With the pnpm global virtual store on, `patch` rewrote the compiler in the shared store. `// @effect-diagnostics-next-line floatingEffect:off` worked; the `effect/floatingEffect:off` form did not.
- `effect@4.1.2` with Bun 1.4.4 and pnpm 12.11.2 (EffectCore research agent): `bun add` and `pnpm add` installs worked; a `Context.Service`, `Layer.effect`, `catchTag`, and `tryPromise` program ran through `BunRuntime.runMain`; an `@effect/vitest` test file passed under `vitest run` and `bun --bun vitest run`.
- Bun 1.4.4: `bun fmt --check` exited 1 on unformatted files and 0 after `bun fmt`; `bun lint` printed `Script not found "lint"` (UserStack research agent).
- Trigger proxy with the draft descriptions (40 queries, one fresh judge over the full skill listing): 20 of 20 should-trigger queries picked the target skill, and 20 of 20 near-miss queries picked a sibling or none.

### Baseline assertions

The write-skill baseline check (Acceptance A8) uses two assertion files in the review scratch directory: `yolo-123/baseline-assertions.md` (CI prompts P1 to P3, assertions A1 to A10) and `yolo-123/effect-baseline-assertions.md` (Effect prompts EP1 to EP3, assertions EA1 to EA8). Each assertion must reward the researched behavior:

- A2 accepts any lockfile-keyed cache choice, including a measured filtered install, because a store cache is not guaranteed to be faster (https://pnpm.io/continuous-integration, https://linear.app/now/ci-bottleneck-reworked).
- A6 accepts a plain install of only the needed Playwright browsers, `--only-shell`, or the Playwright container, and needs no browser cache (https://playwright.dev/docs/ci#caching-browsers).
- A10 accepts `bun check` as a real type checker (since Bun 1.4.3) with a parity check, and rejects it only where declarations or incremental builds are needed.
- EA2 accepts the default exit codes of `effect-tsgo tsc`, which fail on Effect errors and warnings, and needs no severity change.
