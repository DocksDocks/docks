## Goal

New plan records carry no frontmatter, GitHub fields own status, owner and completion, and archive accepts only a merged pull request. The two existing v2 records are converted by the named follow-up plan, so this goal covers records created from here on.

Mode: plan-and-implement

## Research

The record duplicates state GitHub already owns, and every duplicate has two writers with nothing reconciling them. Completion is the visible case: issue #12 closed with `state=CLOSED` and `stateReason=COMPLETED` while its body kept `status: ongoing` and its label kept `plan:ongoing`, observed directly after pull request #13 merged. `stateReason` is already requested in `ISSUE_FIELDS` at `plan.mjs:33` and written by `--reason` at `plan.mjs:812`, yet no code path reads it, so the data needed to derive completion is fetched and discarded.

Six of the seven frontmatter keys are duplicates. `title` repeats the issue title, `goal` repeats the `## Goal` section in the same body, `created` and `updated` repeat `createdAt` and `updatedAt`, and `updated` is stale the moment a label edit bumps GitHub's own timestamp. `assignee` is dead weight: it is pinned to `null` by check 1 while ownership lives in the issue assignee field. `status` repeats the `plan:<status>` label that the same call already writes at `plan.mjs:811`, which is the completion bug one level up. Only `plan_contract` states something GitHub does not.

Frontmatter also renders wrong in the surface that now holds the record. GitHub markdown turns `---` into a horizontal rule, so a v2 issue body opens with a rule, seven loose `key: value` text lines, and a second rule.

Four statuses survive because GitHub has no field for them. `drafting`, `planned`, `ongoing` and `blocked` are open-issue substates recording whether the plan passed review and whether implementation began, which is what makes a plan resumable cold. They belong on the `plan:<status>` label, whose namespace is already reserved and validated. Completion is read from GitHub instead, under one closed truth table: `OPEN` takes its substate from the label whatever the `stateReason`, `CLOSED` with `COMPLETED` is finished, `CLOSED` with `NOT_PLANNED` is retired, and `CLOSED` with `DUPLICATE` is reported as duplicate and parsed no further. Reopening returns an issue to `OPEN`, so no separate reopened state exists.

The contract version travels with the bytes it describes. A v3 body opens with the HTML comment `<!-- plan-contract: v3 -->`, which renders invisibly in the issue UI and survives every label edit. A label would be the wrong home: any triage-capable account can delete it, and a body whose format identity lived on a deleted label would stop parsing, which is the cross-object version of the two-writer bug this plan removes. Labels therefore carry only `plan` and the four phase substates. A body that declares no version by marker or frontmatter is reported unreadable rather than guessed.

A closing keyword closes an issue but never edits its labels, so a merge leaves the phase label behind and a reader sees a closed issue still tagged `plan:ongoing`. That stale tag is the visible half of the drift this plan removes, so the four phase labels are defined as descriptions of open work: every read of a closed issue treats them as absent and derives completion from `state` and `stateReason`, `status` refuses to place one on a closed issue, and the verifier strips any that a merge left behind. Issue #12 is the live exhibit, closed by commit `adbb40a` while still carrying `plan:ongoing`. The refusal path has teeth: of the twelve most recent first-parent commits on `main`, nine were pushed directly and their `associatedPullRequests` connection is empty, so a direct push cannot satisfy the landing check.

Three record-shape decisions were settled with the owner in session. A blocked plan states its reason as the first line of `## Open questions`, spelled `Blocked: <text>`, which keeps the eight-section set closed and gives the reason one writer in the body rather than an unordered comment. An OPEN issue carrying no phase label is reported `unlabelled` rather than defaulting to `drafting`, because a silent default is the same invisible-drift class this plan removes. A close with `stateReason: DUPLICATE` reports the distinct state `duplicate` rather than folding into `retired`, since a duplicate was never abandoned on the merits and folding would contradict the reason GitHub recorded.

Derived completion forbids post-merge steps, which is a contract rule rather than a plan detail. Step mutation refuses unless the plan is ongoing at `plan.mjs:652`, and archive refuses any non-terminal step at `plan.mjs:769`. Once the closing pull request merges, the issue is `CLOSED/COMPLETED` and therefore finished, so a step scheduled after that merge can neither be marked done nor archived past. Every step must be terminal before the closing merge, and post-merge work belongs to a named follow-up plan.

Landing evidence needs a second proof that a direct push cannot forge. Issue #12 is closed and its work is on the default branch, but `closedByPullRequestsReferences` is empty in both the plain and `userLinkedOnly` selections, because the closing keyword lived in the commit message rather than the pull request body: `ClosedEvent.closer.__typename` returns `Commit` with oid `adbb40a910cdb75617c2b7a041f2ae66aacf9b25`. A hand-pushed commit carries no such association.
