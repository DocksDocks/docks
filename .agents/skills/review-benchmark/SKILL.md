# Review benchmark

This skill measures a reviewer change before it ships. It replays frozen review cases through the released reviewer (the baseline) and the working-tree reviewer (the candidate), or through plan-reviewer variants at git refs, at each configuration of model, effort, and service tier. A judge from another model family matches the findings with the known defects. `results.md` holds the decision rule and the results of every run.

The skill is maintainer tooling of DocksDocks/docks-kit: `docks-kit sync` does not ship it. The scripts run on Bun only, from a checkout of this repository with its `node_modules`: `score.mjs` reads plans and review comments with the parser of `docks-kit plan` (`cli/src/plan/records.ts` and `reviews.ts`), and `prepare.mjs` reads the omp pins with `cli/src/engine-native/toolchain.ts` and runs `cli/src/main.ts plan base-blob`. A copy of the skill folder without the `cli/src` folder of the checkout does not run. Run each script as `bun "$skill/scripts/<script>.mjs"`.

| Path (in this skill folder) | Content |
|---|---|
| `scripts/prepare.mjs` | Builds the agent files of the configurations, of the plan-reviewer variants, of the self-review roots, and of the fixer and manager agents, one workspace per case, the probe, the rounds of review loops, and the manager prompts; runs the omp preflight (see omp compatibility) |
| `scripts/score.mjs` | Parses the returned blocks, builds judge pairs, reads and checks the omp transcripts, writes the report with its decision, drift, sequential, stage, and control tables, plans the sample size of a decision from an A/A workspace (`power`), counts the cases with known defects of a corpus (`corpus`), picks the answers of the second judge (`sample`), and plans the fix step of a loop round |
| `scripts/omp.mjs` | Every omp fact that `prepare.mjs` and `score.mjs` rely on (see omp compatibility) |
| `scripts/redact.mjs` | Makes a redacted test fixture from a real omp transcript (see omp compatibility) |
| `scripts/outcomes.mjs` | Lists the reverts and follow-up defects of each landed plan (see Outcomes) |
| `scripts/escapes.mjs` | Freezes production source data and builds the ordered escape draw without network reads |
| `scripts/keys.mjs` | Makes, restores, and checks the encrypted copy of the keys folder off this machine (see Cases, Key backup) |
| `tests/` | The vitest suite of the scripts, with redacted real omp transcripts in `tests/fixtures/omp/` (see Tests) |
| [references/judge.md](references/judge.md) | The judge's instructions: match pass, decision pass, and adjudication pass |
| `cases/dev/`, `cases/heldout/` | Case files and their inputs; held-out answer keys are in `<id>.key.json` |
| `results.md` | Decision rule and the append-only results log |

<constraint>
Held-out cases decide whether a change generalizes, so the person or agent who changes reviewer prompts never sees their defects. That author does not open any file under `cases/heldout/`, and does not open the workspace, `pairs.json`, or `judgments.json` of a held-out run. The author reads only the held-out `report.md`. Held-out cases run once per decision, after the dev iterations.
</constraint>

## Cases

A case is `cases/<split>/<id>.json` plus the files it names in the same folder.

| Field | Kinds | Meaning |
|---|---|---|
| `id`, `kind`, `split` | all | Case name (also the file name), `code`, `code-delta`, `plan`, or `plan-delta`, and `dev` or `heldout` |
| `issue`, `round` | all | Plan issue number and review round that the prompt names |
| `pull` | all | Optional pull request number: the pull request whose head holds a case commit that `origin/main` does not reach, for example a commit of a squash-merged pull request. When a case commit is missing, `case` fetches that head into `refs/review-bench/pull/<n>`, except when `refs/review-bench/pull/<n>` exists: then `case` does not fetch, and stops when that ref does not hold the commit (see Procedure) |
| `cycle` | all | Review cycle of the round; every case of a draw unit has it, because a round number can repeat in another cycle of the same plan (see Cases, C7). Optional for other cases |
| `plan` | all | Plan body file (the plan export; for `plan-delta`, the new body) |
| `base`, `head` | code kinds | Commits; the reviewed tree is `head` plus `patch` |
| `patch` | code kinds | Optional patch that plants defects into `head` |
| `delta_base`, `previous_review` | `code-delta` | Head of the previous round, and that round's comment |
| `seeded` | plan kinds | Optional boolean: `true` when a fixed template plants a defect in the body, `false` for an unseeded body; absent in older cases whose seeded status is unknown |
| `repo_ref` | plan kinds | Repository commit for the plan's facts |
| `previous_body`, `previous_review` | `plan-delta` | Body and comment of the previous round |
| `rejection` | delta kinds | Optional rejection comment of the previous round |
| `external` | all | Optional list of the file fields (`plan`, `patch`, `previous_review`, `previous_body`, `rejection`) whose files are in the key folder |
| `show_benchmark` | all | Optional `true` for a case whose plan changes this skill: the snapshot and the diffs then hold this skill folder without its `cases/` folder (see Workspace) |
| `known` | dev only | Known defects: `id`, `title`, `locator`, and `severity` (code) or `kind` (plan). A code defect adds `fix`, its fix patch (a file in the case folder), and optionally `fix_after`, the ids of the known defects whose patches its patch needs first |
| `protected` | dev only | Optional protected decisions: `id`, `section`, and `summary` of each decision that the user made or delegated: a request correction, a choice of the user that the plan records, or a decision that a yolo plan records under the user's delegation (the plan contract treats it as settled; a reviewer may still report its false premise or broken effect). A reviewer must not re-argue them. The judge pairs each finding with each of them (see the Decision pass of `references/judge.md`), and the report gives the re-argued decisions of each run. They do not count in known or recall |
| `control` | all | Optional `true` for a control case, which has no known defect (see Controls) |

A held-out case file has no `known` field and no `protected` field. Its known defects are in `<id>.key.json`, in the same form as the `known` list of a dev case, and the fix patches are in the folder of the key file. A key file is the list of known defects, or an object with that list in `known` and the protected decisions in an optional `protected` list; a list, or an object without `protected`, gives no protected decisions. `prepare.mjs case` refuses a held-out case file with `known` or `protected`. Of the agents, only the judge reads key files; `score.mjs` and `prepare.mjs loop` read them too. The keys of the current held-out cases are in `cases/heldout/`: plans #100, #109, #111, #113, and #115 published them after their decisions, so these cases build and score without `--keys`. While reviewers run on a new held-out set, keep its keys outside the repository until its decision, because a reviewer can search the checkout: for example in `$XDG_STATE_HOME/docks/review-bench/keys/` with mode 0700. Give that folder to `score.mjs pairs` and `score.mjs report` with `--keys <dir>`. `pairs` then reads `<dir>/<id>.key.json` for each case without `known`, and never the key file next to the case file. `report` stops when a key in that folder has other known-defect ids or other protected-decision ids than `pairs.json`; run `pairs` again.

With `--keys`, every key comes from the keys folder, also the key of a case whose key file is in `cases/heldout/` (plan #109, decision 6). So when a held-out set mixes cases with published keys and cases whose keys stay outside the repository, copy the published `<id>.key.json` files into the keys folder before `pairs`, `report`, and `loop`, and for a code case also its fix patches. A plan known defect has no fix patch, so its key file is enough.

A held-out case can keep its input files in the key folder too: `external` names their fields, for example `["plan", "patch"]`. Give the key folder to `prepare.mjs case` and `prepare.mjs loop` with `--keys <dir>`; without it, they stop before they write. The workspace gets these inputs under its own names (`plan.md`, the snapshot, and the diffs), so no file of the key folder lands in a workspace under its own name.

To add a case, add its case file and its inputs. Use the base, head, and plan of the round that missed the defect, with one `known` entry per defect and a fix patch for each code defect. When `origin/main` does not reach a case commit (`git merge-base --is-ancestor <commit> origin/main` fails), set `pull` to the number of the pull request whose head holds the commit; a unit test fails for a case without it. Grow the corpus from production before planting defects. Apply these rules before reading any candidate:

1. **C1: freeze the population.** Fix an exclusive ISO cutoff and a seed. Run `bun "$skill/scripts/escapes.mjs" snapshot --repo <owner/repo> --closed-before <time> --out <keys>/escape-draw-source.json` once, right after the cutoff. The snapshot holds the complete `fetchRepository` input of `outcomes.mjs`: closed plans with their closing pull-request references, all issues and pull requests with their bodies, labels, creation and merge times and merge commits, and default-branch commits. It also holds every comment, with body and creation time, of each plan closed before the cutoff, the existing case metadata, the cutoff, and the script commit (`git rev-parse HEAD`, or `--commit <sha>`). Run `draw --snapshot <file> --seed <seed> --record <keys>/escape-draw.json --manifest <skill>/cases/escape-draw.md`. Draw reads the snapshot only and leaves out the items, comments, and merges created at or after the cutoff. The snapshot keeps the contents of each item as they are when the snapshot runs, not as they were at the cutoff: an edit of a title, a body, a label, or a comment between the cutoff and the snapshot is a known limit. After the snapshot, no edit on GitHub can change the draw. The frozen part records the commit of the `escapes.mjs` that ran the draw (`Draw script commit`), next to the script commit of the snapshot, so a redraw of one snapshot with other code shows. With `--commit <sha>`, the draw refuses unless the running `escapes.mjs` and `outcomes.mjs` have the blobs of those paths at that commit, in the repository of the current folder; so the scripts can run from the checkout or from a `git archive` of the commit. Without it, the draw takes the commit of the current checkout, with `-dirty` when the running files differ from it. With no output paths it only prints; the same snapshot bytes, seed, and draw commit give the same bytes.
2. **C2: draw rounds, not findings.** One unit is one issue, one reviewer, and one missed round in its review sequence. Put all qualifying findings of that round into one case. Order units by issue number, then reviewer (`code` before `plan`), then sequence (comment time, then round number); distinguish repeated round numbers in separate cycles. Lens blocks of the same round form one round. A later round with new findings is a candidate for the round before it in the same review cycle when a subsequent round confirms the fix; the first round of a new cycle is no escape of the previous cycle. In the format with Previous findings, a later round of the cycle marks the finding fixed or resolved, and an `open` line is a repeat. In old formats without Previous findings, a later review confirms the fix only when it no longer reports the finding text, and a finding with the text of a finding of the round before it is a repeat. Subtract the repeats. Add the follow-up defects of C9 against the code round before landing. Take or reject every unit in order; choose no subset.
3. **C3: fix rejection reasons first.** Reject a finding only because (a) it is on lines the earlier round did not see, (b) no later round confirms its fix, (c) the base, head, or plan body of that round cannot be rebuilt, or (e) it is a follow-up item that is no defect of this plan (C9). The confirmation rule of the draw (C2) only selects candidates. The builder decides (b) for each finding by reading the later rounds of the same review cycle: a later round must mark the finding fixed or resolved, or, in old formats, no longer report the defect, also under a changed locator or wording. So a lenient candidate filter adds at most a unit that is then rejected as (b) with its recorded reason. Reject a unit with no finding left. Reject a unit as (d) when a case for that round existed before the cutoff. Keep every rejection and its reason. Do not run a reviewer on a candidate before the take-or-reject decision.
4. **C4: split by plan.** A plan with a dev case stays dev. A plan with only held-out cases stays held-out. A new plan goes to held-out, which is below the decision limit; dev already has 42 cases. Keep the existing held-out set frozen. This outcome-blind assignment does not establish assumption S (Decisions). Its two known limits are related cases of one plan, which need not be independent, and the 12 plans already in both splits (14, 22, 23, 83, 89, 98, 100, 102, 103, 106, 109, 111). Give the number of distinct plans beside case counts in the corpus-growth report.
5. **C5: finish both escape splits first.** Build dev escapes in the same order and with the same rejection reasons as held-out escapes. Start seeded cases only after every held-out and dev escape has an outcome.
6. **C6: seed only the remaining gap.** Fill the gap for each reviewer, not a chosen share of the corpus. Use only plans with no dev case, ordered by `sha256("<seed>:" + issue)` with the seed fixed in the manifest. Code cases use `patch`. Plan cases use the planting procedure below and carry `seeded: true`; new unseeded plan cases carry `seeded: false`. `prepare.mjs` validates the boolean, and the report counts it in `Seeded cases of the shared cases with known defects`. An older plan case without the field still gives an unknown seeded share, not a claim that it is unseeded.
7. **C7: keep held-out details restricted.** Before any command reads a mixed held-out set, copy every published key and the code fix patches into `$XDG_STATE_HOME/docks/review-bench/keys/` (mode 0700), and give this folder to every `--keys` command. Keep the source snapshot, the restricted record, and the new held-out keys, patches, and `external` inputs there, outside the repository and public records until the decision. The restricted record has a `frozen` object with the ordered units, their issue, reviewer, missed round, split, and finding texts; its separate `outcomes` list records taken or rejected units with reasons. Hash the canonical JSON of `frozen`, including its final newline; append outcomes without changing it. Only the public manifest enters the repository: cutoff, the script commit of the snapshot and of the draw, seed, source-snapshot and frozen-record SHA-256 hashes, unit counts by split and kind, and each dev unit by issue, reviewer, missed round, kind, and commitment (the SHA-256 of the canonical JSON of the unit). The manifest holds no finding text, dev or held-out; all finding texts stay in the restricted record, and a dev case shows its own texts when it is built. Its outcome section gives taken and rejected counts by split and reason, and the outcome of each dev unit by its commitment and reason, never held-out unit identities. After the first decision, a later plan publishes the snapshot, record, and keys; the hashes make them checkable.

   A builder writes one outcome file per decided unit, `<keys>/outcomes/<unit id>.json`, with the fields `unit`, `issue`, `reviewer`, `kind`, `missed_round`, `split`, `outcome` (`taken` or `rejected`), `case` (a taken unit) or `reason` (a rejected unit, a letter of C3), `findings`, `inputs`, `decided` (an ISO time), and an optional `note` (a string that explains a judgment call). The record keeps the note, and the manifest never prints it, because a held-out note can name a defect. Every case of a draw unit carries a `cycle` field with the cycle of its unit, also cycle 1: a round number can repeat in another review cycle of the plan, also in a cycle that gives no unit, so the draw cannot tell from its units when a round is ambiguous. Then run `bun "$skill/scripts/escapes.mjs" outcomes --record <keys>/escape-draw.json --outcomes <keys>/outcomes --manifest <skill>/cases/escape-draw.md [--cases <cases-dir>]`. It refuses an outcome file of an unknown unit, a second file of one unit, a field that differs from the frozen unit, an unknown field, a taken unit without a case file of its issue, split, kind, round, and cycle (a case without `cycle` included), a case that two units name, and a rejected unit without a reason letter; then it writes nothing. Else it writes the `outcomes` list of the record in draw order and replaces the `## Outcomes` section of the manifest, and both frozen parts stay byte for byte. A rerun on the same files gives the same bytes.
8. **C9: follow-up defects, one plan each.** A follow-up item is a candidate only when the follow-up rule of `outcomes.mjs` (see Outcomes) counts it as a defect: a defect label, a defect title, or an `Unreached:` line. That rule leaves out plan work, so a later plan that cites an earlier plan is no candidate, also with a defect title. The outcomes table and the draw use this one rule. Each item goes to exactly one plan: the plan of a landing pull request that it cites (any merged pull request that closed the plan, the set that the follow-up rule takes); otherwise the highest-numbered cited plan that closed before the item was created; otherwise the highest-numbered plan whose follow-up rule took it. Count the corpus without a workspace with `bun "$skill/scripts/score.mjs" corpus --cases <cases-dir> [--keys <dir>]`: it prints the cases with known defects and their distinct plans per reviewer and split.

The first revision of the [audit comment of plan #146](https://github.com/DocksDocks/docks/issues/146#issuecomment-6967065548) exposed candidate plans and rounds, and its edit history stays public. This is a known exposure limit. Prompt authors must not read that issue, its edit history, the restricted files, or the review comments of held-out plans. The agent that builds held-out cases does not change reviewer prompts and reports only paths and counts. A case whose plan changes this skill sets `show_benchmark`, including #135 and #133 or #134 when its diff touches this skill.

Known limit of the draw of plan #146 (C9): the first draw took plan work as follow-up defects, gave one item to several plans, and printed dev finding texts in the public manifest, so the dev section held held-out follow-up texts. The rules above fix this, and the draw runs again on a new snapshot. Before the fix, the manager and the builder read the candidates of the first draw, and the attribution of an item to one plan was written after that reading. No reviewer ran on a candidate, so no unit was chosen by its outcome, which assumption S needs; but this draw does not keep the full rule that no candidate is read before the draw is fixed. Later draws keep the full rule.

### Fixed plan planting procedure

Take plans in the seeded order. Use a rebuildable, unseeded body and its repository ref. For each plan, try the templates in this fixed order: `goal_fit`, `research_gap`, `security_risk`. Use the first applicable template; where several locations qualify, use the first in body order. Record an inapplicable template and its factual reason in the restricted record. One case gets one edit and one known defect, not a combination. Preserve all other text, the repository ref, and, for a delta case, the previous body and review. The input body carries the edit; it needs no code patch. Set `seeded: true`. Keep the original body and the exact edit in the restricted record, and put the known entry in the dev case or the held-out key. Do not select a template by reviewer performance.

| Template | Applicability and the single edit that plants the defect | Known entry |
|---|---|---|
| `goal_fit` | The Goal requires an output that has one delivery step, no other step depends on that step, and another step will remain. Remove that delivery row from the Steps table; leave the Goal and Acceptance unchanged. | `kind: goal_fit`; locator names Goal, Steps, and the required output; title and summary state that no remaining step delivers that output and that the removed step must be restored. |
| `research_gap` | A Research decision names a repository API method that is present at `repo_ref`, and that API has no method named `benchmarkMissingMethod`. Replace only that method name in the decision with `benchmarkMissingMethod`; leave its proposed effect unchanged. | `kind: research_gap`; locator names the edited Research decision; title and summary name the nonexistent method, the real interface at `repo_ref`, and the method name to restore. |
| `security_risk` | A delivery step processes a user-supplied file path under a named root and checks containment. Replace its containment requirement with permission to accept absolute paths and `..` without checking the resolved path; leave its file operation unchanged. | `kind: security_risk`; locator names the edited step; title and summary state the outside-root read or write that the input permits and require a resolved-path containment check before that operation. |

### Key backup

The keys folder of C7 is the only full copy of the held-out details that are not published. The hashes of `cases/escape-draw.md` can check a copy, but they cannot rebuild one. So keep an encrypted copy off this machine, in a private vault repository of the owner, one commit per copy. `scripts/keys.mjs` makes and restores the copy with GnuPG and GNU tar. `backup` and `restore` stop before they read or write anything when the first line of `tar --version` does not contain `GNU tar`: the BSD tar of macOS does not have `--sort=name` and `--to-command`. On macOS, install the Homebrew `gnu-tar` package and put its `gnubin` folder first on `PATH`. A backup needs only the public key of one dedicated backup key pair. A restore needs an export of its secret key, and only the user holds that export. Every agent with the `gh` login of the user can read the private repositories of the account, so the encryption, not the access control, keeps the keys from reviewers. The copy holds the full keys folder, so it also covers every later held-out set whose keys stay there.

1. Make a copy after each change of the keys folder: a snapshot, a draw, an outcome, a key, a patch, or an `external` input. Run `bun "$skill/scripts/keys.mjs" backup --keys <keys> --out <vault checkout>`. `--out` must be the root folder of the vault clone: `git rev-parse --show-toplevel` in it must give that folder. So `backup` refuses a folder that is not in a git checkout and a folder below the root of a checkout. It writes one `keys-<UTC time>.tar.gpg` into the vault checkout and no other file, and it does not change the keys folder. The archive holds a reproducible tar of the folder and a `MANIFEST.sha256` with the SHA-256 and the path of every file. The tar keeps each hard-linked file as a regular file with its own bytes (`tar --hard-dereference`). Before it encrypts, `backup` reads each file back from the tar and compares it with `MANIFEST.sha256`. When a file changed after the manifest, the backup stops, names the file, and writes nothing.
2. The copy is off this machine only after the push. So before each commit and push to the vault, ask the user in the session, also in a yolo run, because the push is an effect outside this repository. With the answer, commit the new file and push it. Keep the older copies.
3. The public key is `backup-key.asc` in the skill folder, in git. It is public and not secret: it can only encrypt, and it tells nothing about the held-out cases. So every clone can make a copy, without an import of the secret key. `backup` reads that file; `--recipient <file>` overrides it, for example in the tests. When the key file is missing or `backup` cannot read it, `backup` stops before it writes anything, and the message names the file. `backup` reads the fingerprint of the key with `gpg --show-keys`. It stops when the fingerprint differs from the `Fingerprint: <hex>` line of the vault `README.md`, or when that line is missing. It encrypts with `gpg --no-options --no-encrypt-to --recipient-file <key file>`, so an options file cannot add a recipient. A key change takes two steps in two repositories. First, a pull request of this repository changes `backup-key.asc`, and nothing else. After its merge, a vault commit changes the `Fingerprint:` line of the vault `README.md` to the new fingerprint; ask the user before this commit and its push, as item 2 says. Between the two steps, `backup` stops on the fingerprint check. This stop is the guard: a changed key file cannot encrypt a copy until the user accepts its fingerprint in the vault.
4. Restore into a new folder outside every git checkout: `bun "$skill/scripts/keys.mjs" restore --archive <vault checkout>/keys-<UTC time>.tar.gpg --key <secret-key export> --out <new dir>`. `--key` is necessary: without it, or when the restore cannot read the key file, the restore stops before it writes anything. The restore never uses the key ring or the agent of `GNUPGHOME`. It makes a new private GnuPG home (mode 0700) in the temporary folder, and runs each gpg command with `--homedir <home>` and without `GNUPGHOME`. It sets `GPG_TTY` to the terminal of its stdin, or removes `GPG_TTY` when the stdin is not a terminal, so a wrong `GPG_TTY` of the caller (for example `not a tty`) never gets to gpg. It imports the export with `gpg --batch --pinentry-mode loopback --import`, and at once decrypts with `gpg --pinentry-mode loopback --decrypt`, with the same agent. When the stdin of the restore is a terminal, the decrypt has no `--batch`, and for a passphrase-protected key gpg asks for the passphrase one time, in the terminal, also over SSH. The stdin of the decrypt is then the terminal, also when the stderr of the restore goes to a file or a pipe. When the stdin of the restore is not a terminal, the decrypt has `--batch`, because without it the loopback prompt of gpg can open `/dev/tty` all the same. Then a protected key stops the restore at once with the gpg error (`Sorry, we are in batchmode - can't get input`), and a key without a passphrase decrypts. The messages of gpg go to the terminal only when the stderr of the restore is one; else the error of the restore holds them. The restore never takes a passphrase on the command line or in the environment, and with no terminal a protected key stops the restore before it writes anything. At the end, also after a failure, the restore stops the agent, removes its socket folder, and removes the home. When one of these steps fails, the restore fails and writes no folder; it keeps the first error and adds one line for each failed step. When `gpgconf --homedir <home> --kill gpg-agent` fails, the restore removes the home all the same, so the imported secret key does not stay on the disk; on Linux, the agent also stops itself when its home goes. After that, `gpgconf` cannot find the agent, so the line names the pid of the agent that `ps` shows: stop it with `kill <pid>`. SIGHUP, SIGINT (for example Ctrl-C at the passphrase prompt), and SIGTERM stop gpg while the home exists; then the restore stops the agent, removes the home, writes no folder, and exits with 129, 130, or 143. It refuses an existing `--out` and an `--out` inside a git checkout, writes the folder with mode 0700, and checks every file against `MANIFEST.sha256`. When git cannot check the folder for a reason other than "not a git repository" (for example, a repository of another owner), the restore stops and names the folder and the git error. Before it writes, the restore lists the members of the archive with `tar -t` and `tar -tv`, and a member that is not a regular file or a folder (for example, a symbolic link or a hard link) stops the restore; the message names each such member. A `MANIFEST.sha256` that is not a regular file also stops the restore. A missing, extra, or changed file stops the restore; the message names the file, and no folder stays. An error about the manifest gives the path or the line number, never the text of a line.
5. Check the restored folder: `bun "$skill/scripts/keys.mjs" check --keys <restored> [--cases <cases dir>]` compares the source snapshot and the frozen record with the `Source snapshot SHA-256` and `Restricted frozen record SHA-256` lines of `cases/escape-draw.md`, and names each field that differs. Then `bun "$skill/scripts/score.mjs" corpus --cases <cases dir> --keys <restored>` must give the same held-out counts as the keys folder.

The first decrypt after an import can fail with `Bad secret key` (or `Bad passphrase` for a protected key) because of a bug of libgcrypt 1.12.0, [T8094](https://dev.gnupg.org/T8094). For an ECC key (for example the cv25519 subkey of a default GnuPG key), the agent fails at random when it first uses the imported key; the result changes with the memory layout, for example with the length of the home path or the size of the environment. [libgcrypt 1.12.1](https://dev.gnupg.org/T8067) fixes it. Plan #162 saw it with GnuPG 2.4.8 and libgcrypt 1.12.0, also when `GPG_TTY` was wrong or the agent restarted after the import; an RSA key did not fail. When `gpg --version` shows `libgcrypt 1.12.0`, `restore` adds one line about T8094 to a failed decrypt only in these cases: the gpg error has `Bad secret key` or `Bad passphrase`, or the restore captured no gpg error text (for example because the stderr of gpg was the terminal), so the error gives only the exit code. Another gpg error, for example `No secret key` or the batch-mode error of a protected key without a terminal, gets no T8094 line, and a stop by a signal gets none. A new run uses a new home and can pass, most of all with another `TMPDIR`, which gives the home path another length. `restore` does not try again by itself.

Restore by hand only when `keys.mjs` cannot run. Over SSH, a plain `gpg --import` can fail, and a plain `gpg --passwd` can wait without end: the agent can open a pinentry window on a desktop that the SSH session does not show. `--pinentry-mode loopback` makes gpg ask in the terminal. Make a fresh scratch folder with `docks-kit scratch new` (mode 0700) for `GNUPGHOME`, and a second one for the plaintext, both outside every git checkout. Set `GPG_TTY` from the real terminal: a shell without a terminal can export a wrong value such as `not a tty`, and the decrypt failures that came with it are the T8094 failures above. Then run these commands, which worked over SSH with the protected key (plan #162, E3). This interactive import asks for the passphrase and converts the key at once, so the agent restart after it does no harm:

```sh
export GPG_TTY=$(tty)
export GNUPGHOME=<fresh scratch folder>
gpg --pinentry-mode loopback --import <secret-key export>
gpgconf --kill gpg-agent
gpg --pinentry-mode loopback --decrypt <copy of the archive> > <plaintext folder>/keys.tar
```

Before you extract it, list `keys.tar` with `tar -t -v -f` and make sure that each member is a regular file or a folder. Then extract it into a new folder and check that folder. `sha256sum -c` checks only the files that the manifest names, and it does not see an extra file. So the last two commands compare the full list of the regular files of the folder, without `MANIFEST.sha256`, with the paths of the manifest. Each manifest line is the SHA-256 (64 characters), two spaces, and the path, so `cut -c 67-` gives the path:

```sh
mkdir -m 700 <plaintext folder>/keys
tar -x -p --no-same-owner -f <plaintext folder>/keys.tar -C <plaintext folder>/keys
cd <plaintext folder>/keys
sha256sum --check --strict MANIFEST.sha256
cut -c 67- MANIFEST.sha256 | LC_ALL=C sort > ../manifest-paths
find . -type f ! -path ./MANIFEST.sha256 -printf '%P\n' | LC_ALL=C sort > ../folder-paths
diff ../manifest-paths ../folder-paths && rm MANIFEST.sha256
```

Stop and do not use the plaintext when a command above fails, when `keys.tar` has a member that is not a regular file or a folder, when `sha256sum` reports a failure, or when `diff` writes a line or exits with a code other than 0. A failure of `sha256sum` or `diff` tells that the folder has a changed, a missing, or an extra file. Else do step 5 with `<plaintext folder>/keys`. Run the cleanup commands below in both cases: after step 5 when every check passes, and at once after a failure. They leave the plaintext folder, stop the agent of the scratch `GNUPGHOME`, and remove both scratch folders, so no imported secret key and no plaintext stay on the disk:

```sh
cd /
GNUPGHOME=<fresh scratch folder> gpgconf --kill gpg-agent
docks-kit scratch remove <fresh scratch folder> <plaintext folder>
```

Protect an export with a passphrase over SSH in the scratch `GNUPGHOME` that holds the key: `gpg --pinentry-mode loopback --passwd <fingerprint>` asks for the passphrase in the terminal, for the key and for each subkey. Then `gpg --pinentry-mode loopback --armor --export-secret-keys <fingerprint> > <export>` writes the protected export.

Key custody (plan #154, D5; plan #162): only the user holds the secret key. A run makes a key pair only with the user's answer in the session. Do the steps for a new key pair in this sequence. First, make the key pair in a scratch `GNUPGHOME` from `docks-kit scratch new`. The user protects the secret key with a passphrase and writes the protected export into that scratch folder, as the paragraph above says. Then the user puts a copy of the export in storage off this machine and confirms it. The user keeps the passphrase off this machine too, apart from the export. Second, do the two steps of item 3: the pull request that changes `backup-key.asc`, and after its merge, the vault commit of the new `Fingerprint:` line. Until that vault commit, `backup` cannot encrypt to the new key. Third, make the first copy to the new key with `keys.mjs backup`, and commit and push it to the vault with the user's answer, as item 2 says. Fourth, test the export: a restore of a fresh clone of the vault with `keys.mjs restore --key <export>`, then `check` and `corpus` on the result. The restore uses its own new GnuPG home, so the export, not the key ring of the scratch `GNUPGHOME`, opens the copy. The user runs that restore and types the passphrase. Then the user checks that the copy off this machine is the tested file: download it back and compare `sha256sum` of the two files, or run the restore with the downloaded file. Fifth, when the test passes and the two files are the same, the run removes the scratch folders with `docks-kit scratch remove`. Until the user confirms the storage off this machine, the test passes, and the two files are the same, the scratch folders stay with mode 0700, and the final report names them as folders that hold a secret, with the command that removes them. Apart from the public key `backup-key.asc`, which is not secret, no secret key, passphrase, fingerprint, vault name, vault content, key location, or machine path goes into this repository, an issue, or a comment.

When the secret key is lost, no one can read the earlier copies again. Start the five steps of the custody rule at once, in their sequence: the new key pair and its protected export off this machine, the two steps of item 3, the first copy of the keys folder to the new key, the restore test of that copy with the new export, and the removal of the scratch folders. When the keys folder is lost too, the held-out cases that only it holds are lost.

## Configurations

A configuration is a model, an effort, and a service tier. `prepare.mjs agents` writes every model at every effort with every tier. The grid of plan #100 is `openai-codex/gpt-6.1-sol` at `low`, `medium`, `high`, and `xhigh`, each with the tiers `priority` and `default`: eight configurations. omp sets service tiers per provider family (`tier.openai`, `tier.anthropic`, `tier.google`), and `scripts/omp.mjs` gives the family of a model from its provider, the part of the selector before the first `/`: a provider that starts with `openai`, `anthropic`, or `google`. Each tier of `--tiers` must be a tier of the family of each model, else `agents` stops and names the tiers of the family. A model whose provider is in no family gets one configuration per effort with the tier `null`: its name has no tier part, it gets no tier override, and `report` does not check its served tier (plan #115). With omp, `agents` refuses a `--model`, `--fixer-model`, or `--manager-model` selector without a provider part, and it prints one line for each model that gets the tier `null`, so that a dropped `--tiers` list is visible. The fixer and the manager follow the same rule: a model of a family takes only a tier of its family, and a model in no family gets the tier `null`, no tier override, and no served-tier check of its entries, and `agents` refuses `--fixer-tier` or `--manager-tier` for it.

| Option of `agents` | Values | Part of the configuration name |
|---|---|---|
| `--model <m>[,<m>...]` | model selectors without an effort suffix; with omp, each selector is `<provider>/<model>` | with two or more models, the model slug (the last path segment, in lower case) and a hyphen come first |
| `--efforts <list>` | omp thinking levels: `off`, `minimal`, `low`, `medium`, `high`, `xhigh`, `max` | the effort |
| `--tiers <list>` | omp service tiers of the families of the models: `openai` takes `none`, `auto`, `default`, `flex`, `scale`, `priority`, and `ultrafast`; `anthropic` takes `none` and `priority`; `google` takes `none`, `flex`, and `priority`. A model in no family drops the list | nothing for `default`, `-fast` for `priority`, `-<tier>` for the other tiers; nothing for the tier `null` of a model in no family |
| `--fixer-model <m>`, `--fixer-effort <e>`, `--fixer-tier <t>` | the model, effort, and tier of the fixer agent; defaults `openai-codex/gpt-6.1-sol`, `high`, and `priority`. | `--candidate-contract-overlay` | none | none: `agents` records the change of the plan contract from `--baseline-ref` to the working tree, and `case` applies it to a copy of the plan contract for each run of a candidate arm (`C1`, `C3`, `Cd`, `P1`, `Pd`, and their control copies); the baseline arms keep the snapshot's contract. `case --loop` refuses a candidate arm with this overlay, because the later rounds of a loop would review without the copy. Use it when a code-reviewer or plan-reviewer candidate also changes the contract (plans #113 and #133) |

For example, `--efforts low,xhigh --tiers priority,default` gives `low-fast`, `low`, `xhigh-fast`, and `xhigh`. With a second model, the names become `gpt-6.1-sol-low-fast` and so on. `--model openai-codex/gpt-6.1-sol,anthropic/claude-opus-5-5 --efforts xhigh --tiers priority` gives `gpt-6.1-sol-xhigh-fast` and `claude-opus-5-5-xhigh-fast`; with `--tiers priority,default`, `agents` stops, because the `anthropic` family takes no tier `default`. The same lists always give the same names, because the report uses them as column names.

Give `--efforts` only the thinking levels that the model supports. Before it changes a file, `agents` runs `omp models find <model> --json` for each model of the configurations, the fixer, and the manager, and stops when omp lists no such model or when the `thinking` list of the model does not hold an effort of a setting (see omp compatibility). omp runs an unsupported level at another level and shows no error (for `openai-codex/gpt-6.1-sol`, `minimal` ran as `low`), so the probe still checks the effort of each message.

### Layouts

The reviewer agents, the self-review skills, and the plan contract are in one of two layouts in a tree of this repository. `score.mjs` holds the table (`PLUGIN_LAYOUTS`), and `prepare.mjs` (`layoutAt`) picks the layout of each ref: `kit` when the tree of the commit holds `SoT/.omp/plugin/agents/code-reviewer.md`, else `legacy`. The working tree, and so every candidate agent and the `worktree` self-review root, has the `kit` layout.

| Layout | Reviewer root: `agents/{code,plan}-reviewer.md`, the reviewer skills, and `skills/[<folder>/]plan-manager/references/plan-contract.md` | Self-review root: `skills/[<folder>/]code-review/` and `code-clarity/` | Refs |
|---|---|---|---|
| `kit` | `SoT/.omp/plugin` | `SoT/.omp/plugin` | the working tree, and the `cli-v*` tags from `cli-v0.25.0` on |
| `legacy` | `plugins/plan-lifecycle` | `plugins/docks` | the `plan-lifecycle--v*` and `docks--v*` tags of the old docks tree, which the variant patches and the recorded baselines of `results.md` use |

`cli-v0.24.0` and older `cli-v*` tags hold no reviewer agents in either layout, so they are no valid baseline, variant, or self-review ref: `agents` stops on them. `agents` prints the layout of the baseline: `baseline <ref> at <commit>: <layout> layout, in <dir>`.

`agents` applies each configuration through omp agent files, so each reviewer runs as a task subagent, as in production:

- `.omp/agents/review-bench-<side>-<role>-<config>.md`: one agent for each side (`baseline`, `candidate`), role (`code`, `plan`), and configuration. The frontmatter pins `model` and `thinking-level`.
- `.omp/agents/review-bench-variant-<name>-plan-<config>.md`: with `--variants`, one plan agent for each variant and configuration, with the model, effort, and tier of the configuration. Its text is `agents/plan-reviewer.md` of the reviewer root of the layout of the variant ref (see Layouts). `agents` extracts that reviewer root at that ref to the folder `variant-<name>-plugin/` next to the baseline copy, and the agent names that folder as its plugin root (see Read scope). `agents` removes the `autoload-skills` key of the copy, because it would load the installed skill, and changes each `skill://<skill>/<path>` to `<plugin copy>/skills/<skill>/<path>`. An agent at a ref before the native omp packages names its plugin root with the plugin root variable of Claude Code, `${CLAUDE_PLUGIN_ROOT}`, and `agents` changes that variable to the plugin copy too. `agents` accepts two forms of the skill path in a variant agent: `skill://plan-reviewer/SKILL.md`, and, at a ref before the native omp packages, `${CLAUDE_PLUGIN_ROOT}/skills/[<folder>/]plan-reviewer/SKILL.md`. It refuses a variant whose agent names its skill in neither form, because the read scope finds the plugin root of a reviewer through that path. Put that path in backticks or quotes, as the plugin agent does: then the path can hold spaces, so the plugin copies can be in a folder whose path has a space. It also refuses a `--baseline-dir` whose folder is the folder of a variant copy, because the variant copy would replace the plugin of the baseline agents, and a `--contract-overlay` variant whose commit or first parent has no plan contract, or whose commit does not change the text of the plan contract. `--full-only` and `--contract-overlay` need `--variants`, and each name in them must be a variant. `agents` makes these checks before it changes a file.
- `.omp/agents/review-bench-fixer.md`: the fixer agent of review loops (see Review loop). It repairs the valid extra findings of a round, with the same model, effort, and tier for every configuration, so that only the reviewer setup varies. Its tools are `read, glob, grep, write, bash`, as lower-case omp tool names.
- `.omp/agents/review-bench-manager.md`: the manager agent (see Stages). It reproduces or rejects each finding of a round with evidence, with one model, effort, and tier for every configuration. It has the tools of the fixer.
- `.omp/agents/review-bench-selfreview-<config>.md`: one self-review agent for each configuration, with the model, effort, and tier of the reviewer agents of that configuration. It is the self-review of the plan manager before code-review round 1 (#98). It loads `skill://code-review` and `skill://code-clarity`, applies both skills to the candidate diff, and returns one block in the code-review block format: the heading, `Code-review: pass` or `Code-review: fixes-required`, and `## Standards` and `## Spec` with finding lines `- [SEVERITY] Category - locator - text`. Its tools are `read, glob, grep`. The agent has no plugin folder, so its text names the path of its own agent file (see Read scope). The arms `S1` and `S3` use it.
- `.omp/agents/review-bench-selfreview-<root>-<config>.md`: with `--self-review-roots`, one self-review agent for each root and configuration, with the text of the self-review agent above. It reads the two skills at the paths of their `SKILL.md` files under the root, which its text names, and no `skill://` URI. For a git ref, `agents` extracts the self-review root of the layout of the ref (see Layouts) to the folder `selfreview-<root>-plugin/` next to the baseline copy; for `worktree`, the root is `SoT/.omp/plugin` of the working tree. `agents` refuses a root without both skills, a repeated name, a copy folder of another copy, and a root agent name that equals a default self-review agent name, before it changes a file. The arms `S1<root>` and `S3<root>` use it.
- `.omp/config.yml`: one entry `task.agentServiceTierOverrides.<agent>` for each agent of a configuration with a tier and for a fixer or manager agent with a tier, with the tier of its configuration, of the fixer, or of the manager. An agent with the tier `null` gets no entry. `agents` reads and writes the file with the YAML parser of Bun and keeps every other setting in it, but a rewritten file loses its comments. With no entry to write, `agents` writes no file. omp lists `.omp/settings.json` as the legacy project file and merges `.omp/config.yml` over it, so `agents` does not write `settings.json`. The script does not change the user's global config.
- `.omp/agents/review-bench-configs.json`: `configs`, the list of configurations, which `case` and `probe` read; `fixer` and `manager`, the model, effort, and tier of these agents; `variants`, one `{ name, ref, sha, delta }` per variant (`delta` is false for a `--full-only` variant), which gives `case` the variant arms; `selfReviewRoots`, one `{ name, source, dir, sha, skills }` per self-review root (`sha` is null for `worktree`), which gives `case` the root arms; and `ompVersion`, the version of the omp of the preflight (see omp compatibility). A `--contract-overlay` variant also has `contractDiff`: the diff of the plan contract from the first parent of the variant commit to the commit. `case --loop` records `fixer` in each loop run (see Workspace), and it stops when the file has no `fixer`. `case` records `manager` as `managerConfig` in each run when the file has it.

omp reads project agents and project settings from the working folder of the session. Write them where the dispatching omp session runs: by default the repository root of `prepare.mjs`, or the folder that `--project <dir>` names (for example the main checkout, when the script comes from a worktree). Give `case`, `probe`, and `clean` the same `--project`. The `.gitignore` of the repository holds `/.omp/`, so the files that `agents` writes in the checkout do not show in `git status`; the repository keeps its own omp config in `SoT/.omp`.

After it writes, `agents` checks with `omp config get` that omp loads every tier override that it wrote (see omp compatibility). `agents` removes the output of an earlier `agents` call before it writes. `clean` removes every `review-bench-*` file of `.omp/agents/`, every `review-bench-*` entry of `task.agentServiceTierOverrides` in `.omp/config.yml` and in a legacy `.omp/settings.json` of an older run, each of these files when no other setting stays in it, and each folder that it empties. It keeps every entry that does not start with `review-bench-`.

The `B3` arm has the candidate prompt, which only names the lens, so it needs a baseline reviewer that loads its lens references itself, such as `main` after plan #98. Both agents can load the lens reference of their skill. The `delta` and `full` prompts of `B1` are the prompts of `C3`, with the baseline agent.

The self-review arms `S1` and `S3` measure the self-review of #98 on the candidate of code-review round 1, as one agent and as one agent per lens. Each run is one review in `run-<k>/blocks/<reviewer>.md`, so `case` refuses these arms with `--loop`. Their blocks have the code-review block format, so `score.mjs` reads them as code-review blocks. The root arms `S1<root>` and `S3<root>` run the same reviews with the skills of a self-review root, so one workspace can compare the `code-review` skill of a release with the working-tree skill, for example `--self-review-roots rel=cli-v0.26.0,wt=worktree` (or a legacy tag such as `rel=docks--v0.22.0`) and `case --arms S3rel,S3wt`.

The variant arms compare plan-reviewer prompts at git refs in one workspace, for example the released prompts and candidates on local refs (plan #109). `case` takes `V<name>` for each variant of the list of configurations, on plan and plan-delta cases only. The prompt of a variant arm is the prompt of `P0` and `P1` in full mode, or of `Pd` in delta mode; only the agent on line 1 differs. One `V<name>` folder holds the plan and the plan-delta runs of a variant, so its report column covers both kinds. On a plan-delta case, a `--full-only` variant runs a full round, so that case measures its prompt and its mode together. A candidate keeps the line `skill://plan-reviewer/SKILL.md` in its agent and puts each new instruction file under `skills/plan-reviewer/`: of a plugin root, the read scope allows only the agent file, the reviewer skill folder, and the plan contract.

Every reviewer reads the plan contract of the case snapshot, so that a later contract fix stays out of the runs. A candidate that also changes the plan contract (plan #109, decision 7) is then measured without its contract change. `--contract-overlay` gives such a variant its contract change: for each run of the variant, `case` copies the plan contract of the snapshot to `run-<k>/plan-contract.md` and applies the change to the copy with `git apply`. `--candidate-contract-overlay` does the same for the candidate arms (see Configurations). The snapshot stays the same. A tree at a ref before the native omp packages holds the plan contract in a category folder, `skills/productivity/plan-manager/`, and a later tree holds it in `skills/plan-manager/`; and the reviewer root is `plugins/plan-lifecycle` or `SoT/.omp/plugin` (see Layouts). So `agents` and `case` find the contract in each tree, the snapshot, each ref, and the working tree, in either folder under either reviewer root. When a change moves the contract, `agents` records only the change of its text, and `case` applies that change to the contract of the snapshot in its own folder. `agents` and `case` stop when a tree holds the contract in more than one of these places. The `meta.json` of the run records `contractOverlay`: `applied`, or `not applicable` when the snapshot contract holds no line that the change removes (blank lines aside), so it does not hold the text that the change changes. The copy then holds the snapshot contract. When `git apply` fails on a snapshot contract that holds a removed line, for example because the context lines differ, `case` stops with the message of git and the run folder, and writes nothing for that case. The prompt of the run tells the reviewer to read the plan contract at the copy and every other repository file under the snapshot root. `case` stops when the snapshot has no plan contract. The runs of every other arm keep the prompt that sends every plan contract read to the snapshot root.

The judge must judge a finding under the contract that its reviewer read: a new contract rule cannot be judged against an old snapshot contract (plan #133). So `case` also copies the contract copy of each such run to `<ws>/contracts/<run label>.md`, where the run label is the blind label of the run in `pairs.json`. The judge reads that copy as the plan contract for the findings of the run (see `references/judge.md`). A `case` call that stops removes the copies that it wrote.

`case` prepares each arm once per configuration, in the arm folder `<arm>-<config>`. `--configs <name,...>` selects the configurations; the default is every configuration that `agents` wrote. One workspace can so hold every configuration of an arm. `score.mjs` reports each arm folder as one arm.

`case` refuses a case folder that exists. To add arms to a case folder, for example a variant with a contract overlay after the first runs, give `--extend`: `case` then adds the folders of the arms and keeps the snapshot, the diffs, and every other arm folder. `--extend` refuses a missing case folder, a case folder whose `case.json` differs from the case file, and an arm folder that exists. When it stops, it removes only the arm folders that it wrote. With `--loop`, it builds the reviewed tree again to get the size of the full diff, which picks the round 1 mode. A code case folder without a base-instructions folder, from an earlier version of the script, gets one.

The base-instructions folder is the input that `plan-manager` writes for a production code-review round. For the repository root and each parent folder of a changed path of the full diff, it holds a copy of each `AGENTS.md`, `CLAUDE.md`, and `REVIEW.md` of the case base commit, under the same relative path. `case` reads each file with `bun cli/src/main.ts plan base-blob <commit> <path>`, the `docks-kit plan base-blob` command of the docks-kit CLI source of the checkout that holds `prepare.mjs` (not the installed `docks-kit`, whose version can differ), as `plan-manager` phase 6 does: the walk lists one path part at a time with `git ls-tree`, a file link and a folder link resolve from the folder of the link, and `..` goes to the parent of the real folder, for at most 40 links. The copy holds the text of the target. A missing path, a folder, a gitlink, a file used as a folder, an absolute, empty, or outside-tree target, and a chain of more than 40 links make the path `absent` (exit status 1). A git command that fails, or any other exit status, stops `case` with the error of the command; it never gives `absent`. `MANIFEST` lists one line per checked path, `copied <path>` or `absent <path>`. The folder of a `code-delta` case also covers the changed paths of its delta diff, from `delta_base` to the reviewed tree, and so does each loop round after round 1, which gets its own folder, still from the case base, for the changed paths of its full diff and of its delta diff. The delta paths matter: a file that the case added and a repair deleted is in the delta diff but not in the full diff. The prompt of a code reviewer names the folder of its round and tells the reviewer to take these instruction files only from it.

`case` writes `config` to the `meta.json` of each run, or of `round-1/` of a loop run: the `name`, `model`, `effort`, and `tier` of the run's configuration. `case --loop` also writes `fixerConfig` to each `round-1/meta.json`: the `model`, `effort`, and `tier` of the fixer agent, from the list of configurations that `agents` wrote. When that list has a manager setting, `case` also writes it as `managerConfig`. For each run of a `--contract-overlay` variant, `case` also writes `contractOverlay`, `applied` or `not applicable` (see Arms). `score.mjs transcripts` adds one entry per reviewer under `reviewers` and keeps every other field:

| Field | Value |
|---|---|
| `seconds`, `tokens` | the time from the first user message to the last assistant message of `config.model`, and the tokens of the messages of `config.model`; without `config`, of every assistant message. The time also counts a failed request (see `messages`) of another model, because its time is real wall time |
| `requestedTier` | the last requested tier (`service_tier_change`) of the tier family of the model: the model of the last `model_change`, else of the first assistant message; `null` for a model in no family (see Configurations) |
| `messages` | for each assistant message, in transcript order: the `model`, the `effort` that was active at the message (the `thinkingLevel` of the last `thinking_level_change` before it, else `null`), and the `servedTier`. A request that stopped on an error (`stopReason` `error`) and has no served tier also gets `failed: true` |
| `sideCalls` | the `model`, `purpose`, and `tokens` of each `model_usage` record, for example a title call of a helper model; their tokens stay out of `tokens` |
| `readScope` | only for a reviewer that called tools: `outside`, the targets of its tool calls outside the inputs of its run; only for a reviewer with such a read, `missing`, the targets of its reads of missing paths, which make no run invalid; and, only for a reviewer that searched the web, `queries`, the query of each web search (see Read scope); `meta.json` keeps no tool calls |
| `diffCoverage` | only for a reviewer with an own diff that has lines: the share of the lines of that diff that the tool results of its `read` calls showed whole, an exact ratio from 0 to 1. The own diff is `focus-<lens>.diff` for a panel lens (also a self-review lens), `full.diff` for `full` and `self-review`, and `delta.diff` for `delta`: in the case folder for a run without round folders and for round 1 of a loop, else in the round folder. A read with a structural summary of the file (`details.summary`) shows no line. A read whose output omp cut in the middle (`details.meta.truncation` with `headRange` and `tailRange`) shows the lines of these two ranges: its `details.displayContent.lineNumbers` cover the whole file, also the lines that omp left out. Else a read shows the lines of `details.displayContent.lineNumbers` when its result has them, with the context lines that omp adds around a range. Without them, it shows the `shownRange` of `details.meta.truncation` when omp cut its output at its end, else the lines of its read selector up to `details.totalLines` (up to the last line of the diff without it). When the result has `details.meta.limits.columnTruncated`, omp cut each line that is longer than `maxColumn` characters. Such a line counts only from a read that shows it whole, a `:raw` read. A read of a list of paths (`a;b`, or the paths that omp records in `details.displayReadTargets`) shows no line of the own diff, also when a path of the list is the own diff. omp keeps no line data for a path of a list, only the text of the result, so its shown lines cannot be identified without a match of the text, which fails for repeated lines. None of the 150 reviews of plan #119 read a diff that way; the rule undercounts such a read, and the read coverage decides nothing. A line of a focus diff also counts when a read of `full.diff` in the same folder showed it: each file section of the focus diff, from its `diff --git` line to the next, maps line for line to the section of `full.diff` with the same `diff --git` line and the same lines. A line that several reads showed counts once; a read without a tool result or with an error result, a read of another file, and a search show no line. A reviewer without a read of its own diff gets 0. The value is an observation: `report` does not make a run invalid for it |
| `ompVersion` | the omp version of the transcript: the `runtime.version` of its last record that has one; no field without such a record (see omp compatibility) |
| `revived` | only for a transcript with more than one user message: `true`. A revived agent appends its next task to the transcript of its first task, so the time and the tokens do not show one review, and `report` makes the run invalid with the reason `revived agent` |

A run of several review rounds keeps each round in a `round-<r>` folder, from `round-1` without a gap, with its own `prompts/`, `blocks/`, and `meta.json`. A round `meta.json` can add `mode` (the round mode), the fix step after the round (`fix`, `fixAlreadyApplied`, `fixedByFixer`, `fixLeftOut`, `fixerChangedNothing`, and `fixRepairedNothing`), and `fixer` (the time, the transcript facts, and the reply of the fixer after the round), see Review loop. `report` reads `config` and `fixerConfig` from the run's `meta.json`, else from its `round-1/meta.json`. A run without round folders is round 1, and its finding ids and scores do not change. Each round folder is a dispatch of its own: the dispatch names of its prompts have `K<round>` after the run part, for example `Code7C1LowR1K2Delta`, and `transcripts` writes the `meta.json` of the round folder.

The snapshot is the reviewed tree without Git history. This skill folder holds the held-out answer keys, so the snapshot, every diff, and the changed-path list of the focus diffs leave it out. A case with `show_benchmark: true`, whose plan changes this skill, gets the skill folder without its `cases/` folder instead, so that the reviewer can check the claims of the plan about the scripts and the skill text. Focus diffs split the changed paths by class:

| Path class | Rule | Focus diffs |
|---|---|---|
| Test | a `test`, `tests`, `spec`, `__tests__`, or `fixtures` folder, or `.test.` or `.spec.` in the name | spec-and-tests |
| Prose | ends in `.md`, `.txt`, or `.rst` | text-and-safety |
| Registry or config | ends in `.json`, `.yml`, `.yaml`, or `.toml` | correctness, spec-and-tests |
| Production | every other path | correctness |

A path can be in more than one class. When no changed path is in a lens's scope, its focus diff is a copy of `full.diff`.

## Read scope

The reviewers run in the working folder of the dispatching session, the live checkout, which holds the fixes of the corpus defects. A reviewer that reads a file outside the inputs of its run can see a fix, so its recall does not count. Each prompt tells the reviewer to give every Read, Grep, and Glob call an absolute path under the snapshot root or a file that the prompt names. The prompt also tells the reviewer that its own instruction files are its agent file and the files of its own skill folder, and that it reads every other file, also the plan contract and other skills, under the snapshot root. The prompt of a run of a `--contract-overlay` variant tells the reviewer to read the plan contract at the copy `plan-contract.md` in its run folder instead (see Arms). It tells the reviewer not to read `skill://code-reviewer` and `skill://plan-reviewer`, because these URIs resolve to another version of the reviewer instructions. `score.mjs transcripts` reads the tool calls of each reviewer transcript and writes the targets outside the inputs to `readScope.outside` of the reviewer entry, each target once, in call order. The `path` argument of a `grep`, `glob`, or `ast_grep` call can hold several targets separated by `;`, as the omp tool docs (`omp://tools/<tool>.md`) tell. The `path` of every other call, for example of a `read` or a `find`, is one target, also when it holds a `;`. When no file or folder has the path of a target, omp can read the target as a list of the paths between `;`, `,`, or white space outside `{}` (`omp://tools/read.md`, Flow step 7), and it resolves a relative path of the list against its working folder. For a `read` call whose tool result records the paths of such a list (`displayReadTargets` in the details of the result), these paths decide, and a path that omp could not read (a `Could not read <path>` note) counts for nothing. For every other target, `transcripts` checks the files as omp does: a target whose whole path exists, with or without its read selector, is one target, for example a snapshot file whose name holds a space or a `;`, or a target in a workspace folder whose name holds a space. Else omp takes the first split that it can: on `;`; on `,` when some part exists; on white space, or on all three delimiters, when each part exists. Without a record, `transcripts` cannot see which paths omp could not read, so each path of the split counts. A URI target is a list only on `;`, and only when each part is a URI. A list target is allowed only when each of its paths is allowed, and `readScope.outside` gets the whole target as the reviewer wrote it. Every other target loses its read selector (for example `:1-260`). A relative path resolves against the `cwd` of the `session` entry of the transcript. The prompt also lets the reviewer read official documentation on the web, but no page of the benchmark repository, as a production reviewer does; the judge gets the same documentation evidence (`references/judge.md`). A `web_search` call has a `query` and no path: `transcripts` writes each query once, in call order, to `readScope.queries`. The query is outside when it targets the benchmark repository, as the paragraph after the list of allowed targets says. `transcripts` also reads the URLs that the tool result of the search cites, and each page among them that can show the benchmark repository is outside, because the reviewer saw its text. A `read` of a local file with an omp JSON query selector (`<file>?q=<filter>`) reads the file before `?q=`. A target is allowed when it is:

- under an input of the run: `snapshot/`, `base-instructions/`, `prompts/`, the `*.diff` files, `plan.md`, `previous-review.md`, and `rejection.md` of the case folder, and of the run folder or of each `round-<j>` folder up to the round of the reviewer
- the copy `plan-contract.md` of the plan contract in the run folder, which the prompt of a run of a `--contract-overlay` variant names (see Arms). It is an input of its run only: the copy of another run is outside. The case-change rule below does not apply to it, because the copy is the contract of the case snapshot with the change of the variant, not a later version of the contract
- under `<ws>/trees/<run label>/` of a round of the run up to the round of the reviewer
- an instruction file of the reviewer, which stays allowed also when the case changes it (see the limit below): `agents/<name>-reviewer.md`, or a file in the `code-reviewer` or `plan-reviewer` skill folder, of the plugin root that the agent text names (the candidate `SoT/.omp/plugin/` of the live checkout, the baseline plugin folder, or the `variant-<name>-plugin/` folder of a variant). `transcripts` finds that root in the system prompt of the `session_init` entry of the transcript. A path in backticks or quotes in the agent text can hold spaces; a bare path ends at the first space. The self-review agent has no plugin root, so its instruction files are its own agent file, `<dir>/.omp/agents/review-bench-selfreview-<config>.md`, which its agent text names, and the two skills that it loads: a `skill://` URI of the `code-review` or `code-clarity` skill, and a file of these skills in an installed plugin copy (see below). For another reviewer, these skill reads are optional instruction reads. The self-review agent of a self-review root reads the two skills only under the root that its agent text names: a file in the `code-review` or `code-clarity` skill folder of `<root>/skills/[<folder>/]`. Its `skill://` reads of these skills and its reads of an installed copy are outside, because they can show another version
- an optional instruction read, when the case does not change its file (see the case-change rule below):
  - the plan contract `skills/[<folder>/]plan-manager/references/plan-contract.md` of that plugin root (this exact file). The plan-reviewer checklist tells the reviewer to read this contract in its own plugin, so the contract is part of the instructions of the reviewer
  - a `skill://` URI of the `code-review` or `code-clarity` skill
  - a file under the folder of one of these two skills in an installed plugin copy, without a `..` segment after the normalization below: a path `<any>/plugins/node_modules/[<scope>/]<package>/skills/[<folder>/]<skill>/…`, the installed kit plugin of omp 19 (for example the package `docks-kit-omp`), or `<any>/plugins/cache/plugins/<plugin dir>/skills/[<folder>/]<skill>/…`, the plugin cache of older omp releases. `scripts/omp.mjs` lists these roots. A `skill://` URI of these skills can resolve to this copy, so the reviewer reads the same text as through the URI
  - a `skill://` URI, or a file in an installed plugin copy, of a skill that no measured plugin copy holds and that is no reviewer skill, for example the always-apply skill `unslop`. The measured plugin copies are the plugin roots and the self-review roots that the agent text names; `transcripts` lists the skill folders under their `skills/` folders, also the skills in a category folder. The key of such a read counts its first and its second path segment as the skill name, because the skill can be in a category folder
- an `artifact://` or `local://` URI: the spilled output of the reviewer, for example `local://<N>.log`
- a web URL that cannot show the benchmark repository: `github.com/DocksDocks/docks-kit`, `raw.githubusercontent.com/DocksDocks/docks-kit`, `api.github.com/repos/DocksDocks/docks-kit`, and the same paths with `docks`, the name before the rename (GitHub redirects it to `docks-kit`), are outside, and so is a page of any other site whose host, path, or query names `DocksDocks/docks-kit` or `DocksDocks/docks`, such as a mirror, a code search, or a GitHub search. A URL that a search result cut with `…` is outside when its text names the owner `DocksDocks`

The benchmark skill itself is outside before every rule above: each local target inside the live `.agents/skills/review-benchmark/` folder (also through a symbolic link, a relative path, or the folder before the first glob segment of a glob), and each `skill://review-benchmark` URI, also one that reaches the skill through `..` from another skill. The skill folder holds the answer keys under `cases/`, and the benchmark skill is no measured plugin skill, so the rule for unmeasured skills such as `unslop` would otherwise allow it.

Every other target is outside: `case.json` (it can hold the known defects of a dev case), `meta.json`, the blocks, the `fixer/` folders (their snapshot holds fixed code), a later round, another run, every other file of the live checkout or of the repository that holds a plugin root (other skills can hold fixed shipped text), every other path, and every other URI, for example `issue://` and `pr://`. For example, `SoT/.omp/plugin/skills/code-review/` of the live checkout is outside, although it is under the candidate plugin root: a skill that the plan names has its production copy, the copy of the reviewed repository, under `snapshot/`. A `grep`, `glob`, `find`, or `ast_grep` call without a path searches the working folder, so it is outside too. A glob is allowed only when the folder before its first glob segment is allowed and no later segment holds `..`. A web search whose query targets the benchmark repository can find its pages, so it is outside, with the target `web_search: <query>`. Outside its `-site:` exclusions, such a query names `DocksDocks/docks-kit` or `DocksDocks/docks`, or names the owner `DocksDocks` without a repository (for example `DocksDocks docks plan-lifecycle archive fix`) while no `-site:` token excludes the repository or the owner. A query that names another repository of the owner, such as `DocksDocks/public`, is allowed. Each URL that the result of a search cites and that the web rule above puts outside gives the target `web_search result: <url>`. A run with an outside target is invalid (see step 4 of the procedure).

Before these checks, `transcripts` normalizes each local target: in the part before its first glob segment, it removes each `.` segment, each doubled `/`, and each `..` segment with the folder before it. So a read through `..`, for example `<run>/round-1/../round-2/full.diff`, counts as a read of the path that it reaches. After a glob segment, a `..` can leave the folder of the glob, so it stays outside.

A read of a path that does not exist shows no file, so it cannot show a fix. `transcripts` marks each tool call whose tool result is an error result (`isError: true`). When each target of such a call that is not allowed is a local path that does not exist (for a glob, the folder before its first glob segment), the target goes to `readScope.missing` and not to `outside`, and it does not make the run invalid. The check reads the files when `transcripts` runs. A read without an error result, a URI, and a path that exists stay outside. The decision table counts these reads per column in `Reads of missing paths` (plan #133 lost 40 of 220 held-out code runs to such reads).

A `skill://` URI of the `code-reviewer` or `plan-reviewer` skill, with or without a path after the skill name, and a file of these skills in an installed plugin copy are outside for every reviewer, and so are the `skill://` URI and the installed copy of every other skill that a measured plugin copy holds. They resolve to the installed kit release, which can be another version than the arm: a baseline reviewer then reads the instructions of another release. The own reviewer skill of a reviewer is the skill folder under its plugin root, which stays allowed. A `skill://` URI that leaves the folder of one skill with a `..` segment counts as a read of the skill that it reaches.

Case-change rule: the reviewer setup under test (the plugin roots and the installed skills) is newer than every case. When a case changes the file of an optional instruction read, the read shows a later version of a file under review, and that version can show the fix. So an optional instruction read is outside when the case changes the same file. `transcripts` compares paths from the skill folder name on:

- the plan contract `<root>/skills/[<folder>/]plan-manager/references/plan-contract.md` gives `plan-manager/references/plan-contract.md`
- an installed copy path `…/skills/[<folder>/]<skill>/<rest>` gives `<skill>/<rest>`, for example `…/plugins/node_modules/docks-kit-omp/skills/code-review/references/perf.md` gives `code-review/references/perf.md`
- `skill://<skill>` gives `<skill>/SKILL.md`, and `skill://<skill>/<rest>` gives `<skill>/<rest>`
- a changed repository path `SoT/.omp/plugin/skills/[<folder>/]<skill>/<rest>` (kit layout) or `plugins/<plugin>/skills/[<folder>/]<skill>/<rest>` (legacy layout) gives `<skill>/<rest>`

The changed files of a run are, for a `plan` or `plan-delta` case, the paths in the Files cells of the `## Steps` table of the `plan.md` of the case folder (split on commas and white space); for a run with round folders, the paths in the `diff --git` and `+++ b/` lines of the `full.diff` of the round (round 1: the `full.diff` of the case folder); and for a single-review code run, the paths in these lines of each diff file of the case folder. `transcripts` stops when such an input file is missing, or when a row of the Steps table does not have 8 cells. The comparison is lexical and conservative. A read is outside when its path and a changed path are the same or one is a folder above the other, so a read of a folder (for example a grep) is outside when a changed file is under it. A glob counts as the folder before its first glob segment, so a glob that could match a changed file is outside. A changed path that ends with `/` or whose last segment has no `.` can be a folder, and a changed folder that can hold skill folders (a folder directly in `skills/`, the `skills/` folder of a plugin root of either layout, or a folder above it, such as `SoT/.omp` or `plugins/<plugin>`) makes every optional instruction read outside.

Limit: the instruction files of a reviewer stay allowed also when the case changes them, because the reviewer cannot work without them: the agent file and the own skill folder of a reviewer, and the `code-review` and `code-clarity` skills of the self-review agent. A reviewer of such a case reads a later version of a file under review, and the read scope does not show it.

## Probe

The probe proves that each configuration reaches its reviewer. Run it after `agents` and before the first case, and again after a change of the model, the omp version, or the tier settings, and after a raise of the omp `verified` pin of `SoT/toolchain.json` (see omp compatibility). `probe` refuses an existing probe folder, so before you probe again, move the old probe folder away or give another `--out`.

1. `bun "$skill/scripts/prepare.mjs" probe --out "$bench/probe"` runs the omp version check of the preflight (see omp compatibility), then writes the case folder `probe/` with an empty `full.diff` and one run `C1-<config>/run-1/` per configuration. The probe changes no file, so its `full.diff` is empty; `transcripts` reads it for the read scope of the run. Its prompt `full.txt` gives the candidate code agent of the configuration a short task with the path of its run folder, because `transcripts` needs a path of the workspace in each task (see step 3 of the procedure). Its `meta.json` records the configuration. When the list of configurations has a manager setting, the run of the first configuration also gets `manager/manager-1.txt`, the same task for the agent `review-bench-manager`, and its `meta.json` records `managerConfig`: the manager has one setting for every configuration, and plan #133 lost its kept recall to a manager served at the tier `null`. `--configs` and `--project` work as for `case`.
2. Dispatch every probe prompt as in step 3 of the procedure, at most 8 at a time.
3. Read the transcripts. The task tool writes `<task name>.jsonl` to the session folder: the path of the dispatching session's `.jsonl` file without the extension. For a nested dispatch, omp can write `<session>/<parent>/<parent>.<task name>.jsonl`, so change the paths of the script below to match.

   ```bash
   sessions="<session folder>"
   bun "$skill/scripts/score.mjs" names "$bench/probe" | while IFS=$'\t' read -r prompt name; do
     echo "$prompt"
     jq -c 'select(.type == "model_change" or .type == "thinking_level_change" or .type == "service_tier_change")
       | [.type, .model // .thinkingLevel // .serviceTier]' "$sessions/$name.jsonl"
     jq -c 'select(.type == "message" and .message.role == "assistant")
       | [.message.provider, .message.model, .message.serviceTier]' "$sessions/$name.jsonl"
   done
   ```

A run used its configuration when its transcript shows these values. The same check applies to every benchmark run: `score.mjs transcripts` records the values in `meta.json`, and `report` checks them (see step 4 of the procedure).

| Transcript entry | Field | Expected value |
|---|---|---|
| last `model_change` | `model` | the model of the configuration |
| the last `thinking_level_change` before each assistant message | `thinkingLevel` | the effort (the effort of that message). A change before the first assistant message is setup |
| last `service_tier_change` | `serviceTier` | the tier for the provider family of the model (the requested tier), for example `{"openai": "default"}`; no check for a configuration with the tier `null` |
| each assistant message | `provider` and `model` | the model of the configuration |
| each assistant message | `serviceTier` | the tier (the tier that served the response); no check for a configuration with the tier `null`, whose messages omp records with `serviceTier: null` |

An assistant message from another model (for example after a usage fallback), a message of the configured model at another effort, or a message of the configured model with another served tier shows that the run did not use its configuration. The served-tier check applies only to a configuration with a tier: a configuration with the tier `null` (a model in no tier family) has no tier to prove. A failed request, an assistant message with `stopReason` `error` and no `serviceTier`, stays out of the model and served-tier checks, because no model served it.

## omp compatibility

`scripts/omp.mjs` is the one place for the omp facts that the scripts rely on: the project agent folder `.omp/agents/`, the project config `.omp/config.yml` and the legacy `.omp/settings.json`, the settings `task.agentServiceTierOverrides`, `task.enableEffort`, and `task.structured`, the agent frontmatter keys (`thinking-level` and its levels, the other model and effort keys, `autoload-skills`), the tier families, the tool names, the URI schemes, the installed-skill paths, the reply rule, the dispatch cap, and the transcript records and fields that `score.mjs` reads. These facts hold for the omp releases from the omp `floor` to the omp `verified` pin of `SoT/toolchain.json`. When an omp release changes one of them, change it in `omp.mjs`: `prepare.mjs` and `score.mjs` import each fact from there.

Three checks stop a run on an omp change that they can see:

1. The preflight of `agents` and `probe` needs no model call. Both run `omp --version`, which must print `omp/<version>`. Below the `floor`, both stop. Above `verified`, both print a warning, because the shape check and the probe must first show that the newer release still gives the facts that the scripts read. Before it changes a file, `agents` also checks the efforts of each model with `omp models find <model> --json` (see Configurations). After it writes, `agents` runs `omp config get <key> --json` in the `--project` folder: each tier override that it wrote must show with its tier in `task.agentServiceTierOverrides`, and `task.enableEffort` must not be `true`, because the `effort` of a task would then replace the pinned `thinking-level` of the agent. It prints the value of `task.structured`, which selects the reply rule below. When this last check stops `agents`, the agent files stay: run `clean`. `agents` records the omp version as `ompVersion` in `review-bench-configs.json`.
2. The shape check of `transcripts` runs on each transcript that `transcripts` picks, before it changes a `meta.json`. These records must be in the transcript: `session` with a number `version`; `model_change` with a string `model`; `thinking_level_change` with a string `thinkingLevel`; and an assistant `message` with a string `timestamp`, strings `message.provider` and `message.model`, and the numbers `message.usage.input`, `cacheRead`, `cacheWrite`, and `output`. Each `model_change`, `thinking_level_change`, assistant `message`, and `toolResult` message also needs a string `runtime.version`, the omp version that wrote it. Each `toolCall` part of an assistant message needs a string `name` and an object `arguments`, and each `toolResult` message a string `message.toolCallId` and a boolean `message.isError`. A missing record, a missing field, a field of another type, and records of more than one omp version (`runtime.version`) stop `transcripts`, and the message names each difference, for example `thinking_level_change.thinkingLevel is missing` or `model_change.runtime.version is of type number, not string`. The check runs on the output of the omp in use, so it also stops a release above `verified` that changed a field.
3. The omp version check of `report`: each transcript entry in `meta.json` has the omp version of its transcript (`ompVersion`, see Workspace). `report` stops when an agent of a run with a `config` has transcript facts without `ompVersion` (for example an entry that an older `score.mjs` wrote; run `transcripts` again), and when the runs of the workspace name more than one omp version. It names the agents or some runs of each version, because another omp release can dispatch, read, or count in another way. Run all runs of a workspace with one omp.

The scripts also rely on these facts of omp 19:

- Reply rule: a task agent replies with the text of its last assistant message. An agent that has the `yield` tool (an agent with an output schema, or with `task.structured: true`) replies with the arguments of its last `yield` call. omp 19 gives a subagent no `yield` tool by default (`task.structured` is `false`). So `transcripts` reads the reply of a fixer from the arguments of the last `yield` call when the transcript has one, else from the text of the last assistant message with text (see Review loop).
- Revived agents: omp can revive a finished subagent with a new task, and the new task goes into the same transcript. A transcript with more than one user message makes its run invalid with the reason `revived agent`: for a reviewer or a fixer in the validity check of `report`, and for a manager in the manager stage (see Stages). Dispatch each prompt as a new task; do not send a second task to a finished agent.
- Dispatch cap: from 9 concurrent subagents on, omp moves the runs to worker threads. So dispatch at most 8 agents at a time, so that every arm runs the same way. `case` and `probe` print `dispatch at most 8 agents at a time, so that every arm runs the same way`.
- Installed skills and spill files: omp 19 installs the kit plugin under `<omp home>/plugins/node_modules/<package>/skills/`, and writes a spilled output as `local://<N>.log` (see Read scope).

### Fixtures

Most tests of the suite (see Tests) build their transcript records by hand, so they cannot show an omp format change. So `tests/fixtures/omp/` also holds real omp transcripts, redacted with `scripts/redact.mjs`: the frontmatter-pinned reviewer and manager runs of a probe, a code-reviewer run with reads, a nested dispatch (`<parent>/<parent>.<name>.jsonl`), a slice of a main session with `model_usage` side calls, and a frontmatter-pinned agent whose requests failed (`FailProbeFlex.jsonl`: the codex API refused the tier `flex`, omp wrote a retry-fallback `model_change` to another model, and the request of that model failed too). The redaction keeps the `type` and the key set of each record and the fields that `score.mjs` reads, puts each path under a fixed fake root, and removes credentials, provider payloads, cost, and message text. The fixture tests parse the fixtures and run the shape check on them, and they fail when the `runtime.version` of a fixture is below the omp `verified` pin of `SoT/toolchain.json`. A synthetic test adds the failed-request cases that the fixture does not show: a served message next to a failed one, and a message that stopped on an error with a served tier.

So a raise of the `verified` pin fails the fixture tests until new fixtures exist. After you raise the pin:

1. Run the probe on the new omp at one cheap configuration, as in step 2 of Run the grid for a new model: `agents`, `probe`, the dispatch of the probe prompts, and `transcripts` on the probe. The preflight, the shape check, and the probe checks must pass.
2. Capture new fixtures with `bun "$skill/scripts/redact.mjs" <in.jsonl> <out.jsonl> [--lines <n>[-<m>][,...]] [--home <dir>] [--keep-reply]`: the reviewer and manager transcripts of the probe (with `--keep-reply`, so the reply `ready` stays), and, for the other kinds of fixture, transcripts of real sessions on the new omp (`--lines` cuts a main session to a slice). The script moves paths under the home folder to `/fixture-home`, replaces other text with `redacted`, and stops when the output still names the home folder. Replace each old fixture with a new one of the same kind, and read each new fixture for a secret, a personal path, or message text that the redaction left.
3. Update the fixture tests for each fact that changed, and update `omp.mjs` when an omp fact changed. Then run the suite (see Tests).
4. Run `clean` on the probe project, and delete the probe workspace.

## Review loop

A loop run replays a code-review loop of plan-manager (`plan-contract.md`, Code-review rounds) on one run of a `code` case, with the round policy that the `meta.json` of the run records. Each round is a folder `run-<k>/round-<r>/`. The judge's answers score each round and decide the fix step, but they do not end the loop: the loop ends after a round that leaves no finding open, or after round 5. Plan cases run one round per run.

1. Build the workspace with `case --loop`. With `--loop`, an arm gives the side of the agent and the round policy of the loop. The fix step is the same for every policy.

   | Policy | Arms | Round modes |
   |---|---|---|
   | `panel-delta` | `C3`, `B1`, `B3` | the rules of plan-lifecycle 0.17.1, the production loop. Round 1 is a `panel` round when the full diff changes 50 or more lines (added plus removed lines), else a `full` round. A later round is a `delta` round when step 6 allows it, else a `panel` or `full` round by the same size rule |
   | `full-delta` | `C1` | the rules of `panel-delta` with one full reviewer: a `full` round where `panel-delta` gives a `panel` round |
   | `full` | `B0` | the policy of plan-lifecycle 0.16.0, which had no panel round and no delta round: every round is a `full` round on the full diff |

   Two arms of one side so run different loops, and one workspace can hold them all, for example `--arms B0,B1,C1,C3`. `case` refuses `S1` and `S3` with `--loop` (see Arms), and `--loop` takes `code` cases only. Each run gets `meta.json` with `policy`, the round policy of its arm, and `round-1/` with the prompts of the round-1 mode. The `meta.json` of `round-1/` holds `config`, `fixerConfig` (the fixer setting, see Workspace), `mode`, and `fullLines`. `loop` takes the round policy from the `meta.json` of the run, not from the arm. It stops when that `meta.json` records no policy or a policy that is not in the table above. The loops of the plan #100 grid in `results.md` ran before the arms had round policies: they used the rules of `panel-delta` under the arm name `C1`, and their runs have no `meta.json` with a policy. To continue such a loop under its own rules, write `{ "policy": "panel-delta" }` to the `meta.json` of its run folder.

   ```bash
   bun "$skill/scripts/prepare.mjs" case --case "$skill/cases/dev/<id>.json" --arms C3 --runs 3 --out "$bench/dev" --loop
   ```

2. Dispatch the prompts of the last round folder of each run, as in step 3 of the procedure, and save each block in `blocks/<reviewer>.md` of that round folder. `score.mjs names` prints the task name of each prompt, with the round after the run part, for example `Code7C3LowR1K2Delta`.
3. Score and judge the round: run `score.mjs findings` and `score.mjs pairs`, and dispatch the judge as in step 4 of the procedure. `judgments.json` keeps the answers of the earlier rounds and gets an answer for each new candidate pair and a rating for each new finding without a `match` answer. For a round after round 1, the judge reads the reviewed tree in `<ws>/trees/<run label>/`, because the loop has changed the tree since the case snapshot. When no finding needs an answer, for example after a round without findings, do not dispatch the judge: `loop` and `report` read a missing `judgments.json` as a file without answers.
4. Run `loop` on the run folder:

   ```bash
   bun "$skill/scripts/prepare.mjs" loop --run "$bench/dev/<id>/C3-<config>/run-1" --cases "$skill/cases"
   ```

   `loop` reads `findings.json`, `judgments.json`, and the known defects of the case. It works on the last round, round r, and stops before the fix step in these cases:

   - Round r did not complete: a reviewer of the round has no block, a block without a verdict line, or the verdict `blocked`. `loop` names each such reviewer with its reason (`no block`, `no verdict line`, or `blocked`). The production loop dispatches such a reviewer again before it posts the round. Dispatch it again, replace its block, and do step 3 again.
   - The judge did not answer a candidate pair of a finding of round r, or did not rate a finding of round r that has no `match` answer. `loop` names the missing answers, as `report` does. Get them from the judge and run `loop` again.

   Then `loop` plans the fix step for the findings of round r:

   | Finding of round r | Fix step |
   |---|---|
   | matches a known defect | the `fix` patch of the defect, after the patches that its `fix_after` list needs. A needed patch that no finding of the round matched and that no earlier round fixed is pulled in. A defect that an earlier round fixed also gets its patch, because a later repair can bring the defect back. Step 6 drops a patch when the tree of round r still holds the fix, and gives the fix step when a patch does not apply |
   | has no `match` answer and the rating `valid` | a patch from the fixer agent |
   | has no `match` answer and the rating `wrong` or `unknown` | a line in `rejection.md`, with the judge's reason as the evidence |

   When the plan has no fix patch and no valid extra finding, or when r is 5, `loop` prints that the loop ends and writes nothing.
5. When round r has findings for the fixer, the first `loop` call writes `round-<r>/fixer/` and stops with the list of the findings. The findings for the fixer are the valid extra findings and the findings that match a known defect whose fix patch does not apply (step 6). A round has one fixer, as production has one manager who repairs every finding of a round together. `fixer/snapshot/` holds the tree of round r after the fix patches that apply, and `fixer/fixer-1.txt` is the fixer prompt: it lists each finding for the fixer with its id and finding line, and names the snapshot, the plan export, and the patch file `fixer/fixer-1.patch`. Dispatch the prompt one time: the agent is `review-bench-fixer`, and the task name is the one that `names` prints, for example `Code7C1LowR1K1Fixer1`. `names` lists the fixer prompt only until `fixer/fixer-1.patch` exists (an empty patch also counts); `transcripts` still finds the transcript of the fixer after that. The fixer repairs each listed finding that the snapshot still shows. A finding that the snapshot no longer shows, because a fix patch of the round or an earlier repair already repaired it, needs no change. The fixer writes all repairs as one unified diff to `fixer/fixer-1.patch`, or an empty file when no listed finding needs a change, and replies with one line per finding id: `repaired` or `not present`. Then run `loop` again. For tests, you can also give one patch that repairs every finding for the fixer with `--fixer-patch <file>`; then delete the fixer prompt of the round, because `transcripts` expects a transcript for each prompt. Such a round has no transcript facts of a fixer, so `report` makes the run invalid (`round-<r>/fixer-1: no transcript facts`, see step 8): do not use `--fixer-patch` for a run that you measure. A `fixer-2.patch` or higher in `fixer/` comes from the earlier design with one fixer per finding, and `loop` stops with its name: delete the patch files in `fixer/` and run `loop` again.
6. `loop` applies the fix patches in plan order, then the fixer patch, to the tree of round r with `git apply`. An earlier repair can change the lines of a fix patch, so a fix patch that does not apply after the patches before it does not stop `loop`:

   | Fix patch that does not apply | Fix step | Field of `round-<r>/meta.json` |
   |---|---|---|
   | applies in reverse: the tree already holds the fix | none, and later rounds count the defect as fixed | `fixAlreadyApplied` |
   | of a known defect that a finding of round r matches | the fixer repairs each finding of round r that matches the defect (step 5), and later rounds count the defect as fixed | `fixedByFixer` |
   | pulled in: no finding of round r matches its defect | none, and later rounds do not count the defect as fixed | `fixLeftOut` |

   A fix patch that applies in reverse shows that the tree of round r already holds the fix, so the findings that match its defect do not stand. `loop` uses this check also for a defect that an earlier round fixed. When round r has no valid extra finding and each fix patch of a matched defect applies in reverse, no finding of round r stands: `loop` prints that the loop ends and writes nothing.

   A missing fix patch, or a fix patch that git cannot read, stops `loop`. Which fix patches apply depends only on the tree of round r and the fix patches, so each `loop` call on round r sorts the patches into the same rows, also the call after the fixer wrote its patch. An empty fixer patch changes nothing. `loop` compares the tree hashes before and after the fixer patch. When the fixer patch leaves the tree as the fix patches left it, the fixer repaired no finding, and `loop` records `fixerChangedNothing: true`. A pulled-in patch repairs no finding of round r, also when it changes the tree. So when no fix patch that is not pulled in applied and the fixer patch changed nothing, the fix step repaired no finding of round r, for example when the fixer finds each listed finding `not present`. Production rejects a finding that does not reproduce, so the loop ends: `loop` adds `fix`, each field of the table above that has a defect, `fixerChangedNothing`, and `fixRepairedNothing: true` to `round-<r>/meta.json`, prints that the loop ends, and writes no round folder. Else `loop` commits the result as the reviewed head of round r + 1, with the head of round r as parent (for round 1, the case head) and the author and committer `Review loop`. No branch or tag points to these commits, so finish each loop before `git gc` can prune them (two weeks by default). Then `loop` adds `fix` (the fix plan: `fixes`, `extras`, and `rejections`) to `round-<r>/meta.json`, each field of the table above that has a defect, with the ids of its defects, and `fixerChangedNothing` when it applies. Then it writes `round-<r+1>/`:

   | File | Content |
   |---|---|
   | `snapshot/` | the new tree, without this skill folder |
   | `base-instructions/` | the instruction files of the case base for the changed paths of the new full diff and of the new delta diff (see Workspace) |
   | `full.diff`, `delta.diff` | the diff from the case base, and the diff from the head of round r; a `panel` round also gets the focus diffs |
   | `previous-review.md` | the blocks of round r in reviewer order |
   | `rejection.md` | only when round r has rejected findings: `Rejected review findings, round <n>`, then each finding with its evidence |
   | `prompts/`, `blocks/` | one prompt per reviewer of the round mode, and an empty folder |
   | `meta.json` | `config`, `mode`, `head`, `repairsOnly`, `fullLines`, and `deltaLines`. The `loop` call after round r + 1 adds `fix`, `fixAlreadyApplied`, `fixedByFixer`, `fixLeftOut`, `fixerChangedNothing`, and `fixRepairedNothing` as for round r |

   The round policy in the `meta.json` of the run picks the mode (see step 1). Under `panel-delta` and `full-delta`, the mode follows `plan-contract.md`: `delta` only when round r completed (each block has the verdict `pass` or `fixes-required`; `loop` refuses every other round, see step 4), no pulled-in patch changed the tree (`repairsOnly`: each change repairs a finding of round r), and the delta diff is at most half the full diff. Otherwise the size rule of round 1 gives `panel` or `full`, and `full-delta` gives `full` in place of `panel`. Under `full`, every round is a `full` round. `loop` also writes the judge's copy of the new tree to `<ws>/trees/<run label>/`, where the run label is the label of the round in `pairs.json`.
7. Do steps 2 to 6 again for round r + 1, until `loop` prints that the loop ends.
8. After the last dispatch of the workspace, run `score.mjs transcripts`, then `score.mjs report`. `transcripts` fills the reviewer entries of each round folder. For the fixer of round r, it writes `fixer` in `round-<r>/meta.json`: `agents` (the time, tokens, and transcript facts of the fixer, under `fixer-1`), `seconds` and `tokens` (the time and tokens of the fixer), and `replies` (each finding id that the reply of the fixer names, with `repaired` or `not present`; no field when the reply names no finding). By the reply rule of `scripts/omp.mjs` (see omp compatibility), `transcripts` reads each line of each string in the arguments of the last `yield` call when the transcript has one, else each line of the text of the last assistant message with text. omp 19 gives the fixer no `yield` tool by default, so its reply is its last message. `report` checks the transcript facts of each fixer against the fixer setting of the loop (`fixerConfig`), as it checks a reviewer against the configuration (see step 4 of the procedure). A loop whose fixer ran another setting is invalid, and the reason names the round, for example `round-2/fixer-1: effort low, not high`. A fixer transcript with more than one user message makes the loop invalid with `round-<r>/fixer-1: revived agent`. A round whose fix step gave findings to the fixer (`fix.extras` or `fixedByFixer`) must have the transcript facts of its fixer, because a repair by hand or by another agent changes the later rounds. Without a fixer entry, for example after `--fixer-patch` or when `transcripts` found no transcript of the fixer, the loop is invalid with `round-<r>/fixer-1: no transcript facts`.

For held-out cases, give the key folder with `--keys <dir>` to `case`, `loop`, `pairs`, and `report`. `loop` then reads the key and the fix patches from that folder.

In `## Configurations: <split>`, the table `### Code loops: <split>` gives these rows for the loops of the case group:

| Rows | Content |
|---|---|
| `Model`, `Effort`, `Served tier` | the models, efforts, and served tiers of the reviewer messages of the loops, from the transcripts, as in the decision table |
| `Round <r> seconds median`, `min`, `max`, `Round <r> modes`, `Round <r> known found per run` | the time, the mode counts, and the known defects found of round r, over the loops that reached round r |
| `Rounds median`, `Rounds max` | the rounds of each loop |
| `Loop seconds median` | the sum of the round seconds of each loop; the fix steps stay out |
| `Known found per run`, `Escaped per run` | the known defects that the loop found by its end, and the others |
| `Valid extras per run`, `Extra-only rounds per run` | the valid extra findings, and the rounds that only extra findings caused: rounds whose previous fix step repaired valid extra findings and no known defect. The fixer repaired the valid extras when it got them (step 5), the fixer patch changed the tree (no `fixerChangedNothing`), and the fixer did not reply `not present` for each of them (`fixer.replies`). A known defect that a finding of a round matches counts as repaired when its fix patch applied, or when the fixer got it (step 6), the fixer patch changed the tree, and the fixer did not reply `not present` for each finding of the round that matches the defect. A defect whose fix the tree already held, such as a repeat of a fixed defect or a defect that an earlier fix step pulled in, needs no repair, so it causes no round |
| `Loops with a fixer`, `Fixer seconds median`, `Fixer tokens median` | the loops that have `fixer` in the `meta.json` of a round, and the sum of `fixer.seconds` and the sum of `fixer.tokens` over the rounds of each loop, over these loops only |

## Stages

The report scores three stages of a review, as production runs them: the raw reviewer findings, the findings that the manager keeps, and the end of the review loop.

1. Run `agents` with the manager options or their defaults, then build the workspace. `case` records the manager setting as `managerConfig` in each run (see Workspace). A run without it takes no part in the stage.
2. After you save the blocks of a round, run `score.mjs findings`, then `bun "$skill/scripts/prepare.mjs" manager --ws "$ws"`. It writes `manager/manager-1.txt` in the folder of each round with findings: the run folder, or the round folder of a loop. The prompt names the inputs that the reviewers of the round had: the snapshot, the plan export, the full diff or the plan diff, and the base-instructions folder. A delta round, whose reviewer prompts give `Round mode: delta.`, also gets the delta diff (on a code kind), the previous round comment, and the rejection comment when the round has one. It skips a round with a block that holds no review and a run without `managerConfig`, and it names both. A prompt whose findings changed is written again, and its old verdict file goes.
3. Dispatch each manager prompt that `names` lists; line 1 names the agent `review-bench-manager`. The manager tries to reproduce each finding in the snapshot of its round. It writes one line per finding to `manager/verdicts.md`: `<finding id>: reproduced - <evidence>` or `<finding id>: rejected - <evidence>`. `names` lists a manager prompt until that file exists. The verdicts do not change the fix step of a loop: the judge's answers still drive it.
4. `transcripts` writes `manager` to the `meta.json` of the round: `seconds`, `tokens`, and the transcript facts under `agents`. A manager transcript of a round with findings that has more than one user message gives the reason `round-<r>/manager-1: revived agent` (`manager-1: revived agent` in a run without round folders), so the run has no complete manager stage.

`report` adds `## Stages`, with one table per case group and one column per arm folder, from the valid runs of cases that are no control case. Each recall row pools the runs: the sum of the found known defects, divided by the sum of the known defects.

| Row | Content |
|---|---|
| `Runs with a complete manager stage` | the runs in which each finding has a verdict, in which the manager transcript facts of each round with findings show `managerConfig` (as a fixer shows `fixerConfig`), and in which no manager transcript shows a revived agent; a run without findings is complete |
| `Raw recall` | the known defects that the findings of all rounds matched |
| `Kept recall` | the known defects that a finding matched that the manager reproduced |
| `Final loop recall` | the known defects that a fix step of the loop repaired, as the `Extra-only rounds per run` row counts a repair (see Review loop) |
| `True findings rejected per run` | the rejected findings that matched a known defect or that the judge rated `valid` |

Kept recall and the rejected row show `n/a` unless every run of the column has a complete manager stage, for example in a workspace that `case` built before the manager existed. Final loop recall shows `n/a` unless every run of the column is a loop. `### Incomplete manager stages` names each run that takes part without a complete stage, with its reasons. The stages change no other table.

## Controls

A control case is a change that landed without a later revert or defect fix: a case with `control: true` and `known: []`. It measures the wrong findings of a reviewer on clean code. `report` adds `## Controls`, with one table per case group and one column per arm folder, from the valid runs of control cases: the findings, wrong, unknown, valid extra, and unjudged findings per run. The control runs stay in the other tables, where they add findings and no known defect. `pairs.json` does not mark a control case, so the judge rates its findings as any other findings. `pairs` refuses a control case with a known defect.

To add a control case, choose a landed plan with no revert and no follow-up defect in the `outcomes.mjs` table (see Outcomes), and use no plan number that names a held-out case. Take `head` from the merge commit of its landing pull request and `base` from the first parent of that commit. Take the plan file from `gh issue view <n> --json body --jq .body`. Match the full-diff size to a dev code case. The dev controls of plan #133 have 880 (`code-119-control`, with `show_benchmark`), 1927 (`code-123-control`), 939 (`code-126-control`), and 72 (`code-129-control`) changed lines, against the dev code cases `code-57-pr58` (838), `code-22-pr24` (1732), `code-96-r1` (1405), and `code-23-pr26` (275). No clean landed plan was as large as the three largest dev code cases.

## Run the grid for a new model

This section measures a new reviewer model with the same tables as plan #100. The model, the efforts, and the tiers are parameters. The cases, the arms, and the decision rule do not change. Run the commands below in the checkout whose skill version you use; `$project` is only the checkout from which omp dispatches the reviewers. Dispatch every prompt of a workspace from one omp session that runs in `$project`, because `transcripts` reads one session folder. Run only one benchmark at a time per dispatching checkout: `agents` and `clean` remove every `review-bench-*` agent file and tier override of `$project`, and `clean` removes `$project/.omp/` when nothing else is in it.

Give `--efforts` only the thinking levels that `omp models find <model>` lists: `agents` stops on another level (see Configurations). omp runs an unsupported level at another level and shows no error, so the probe in step 2 still checks the effort of each message. The baseline ref is the last docks-kit CLI release on `origin/main` (a `cli-v*` tag of the kit layout); a legacy `plan-lifecycle--v*` or `docks--v*` tag is still a valid baseline, of the legacy layout (see Layouts). In a linked worktree, `--git-path docks-review` gives a folder of that worktree. That folder is also correct, because the workspace must only be outside the reviewed snapshots and readable by the reviewers.

```bash
repo="$(git rev-parse --show-toplevel)"
skill="$repo/.agents/skills/review-benchmark"
bench="$(git rev-parse --path-format=absolute --git-path docks-review)/bench-<label>"
ref="$(git describe --tags --match 'cli-v*' --abbrev=0 origin/main)"
project="<dispatching checkout>"
bun "$skill/scripts/prepare.mjs" agents --baseline-ref "$ref" --model <model> --efforts <list> --tiers <list> \
  --project "$project" --out "$bench/dev"
```

1. `agents` runs the omp preflight (see omp compatibility), then writes to `$project/.omp/agents/` one agent file for each side, role, and configuration, one self-review agent for each configuration, the fixer agent `review-bench-fixer`, the manager agent `review-bench-manager`, and the list of configurations. With `--variants`, it also writes one plan agent for each variant and configuration, and the plugin copy `variant-<name>-plugin/` of each variant next to the baseline copy. It writes the tier of each agent of a configuration with a tier to `task.agentServiceTierOverrides` in `$project/.omp/config.yml`, and checks with `omp config get` that omp loads each of them (see Configurations). Dispatch the reviewers from the top-level omp session, or from a subagent that you start after `agents`: in the a6 check of plan #100, a subagent that started before `agents` dispatched reviewers with the parent's tier, not with the override.
2. Probe: run `bun "$skill/scripts/prepare.mjs" probe --out "$bench/probe" --project "$project"`, dispatch its prompts, and run `bun "$skill/scripts/score.mjs" transcripts "$bench/probe" --omp-sessions <session folder>`. Each line of the command below gives the configuration name, the configuration effort, and the configuration tier, and then, for each reviewer, the efforts of its messages, the requested tier, and the served tiers. The message efforts must hold only the configuration effort. For a configuration with a tier, the requested tier must equal the configuration tier, and the served tiers must hold only the configuration tier (see Probe). A configuration with the tier `null` has no tier check: it is a model in no tier family. Do not continue until each line does. When the requested tier is another tier, the dispatching session did not use the override: dispatch the probe again from a session or subagent that started after `agents`. To probe again, for example after a new `agents` call, move `$bench/probe` away first or give another `--out`, because `probe` refuses an existing probe folder.

   ```bash
   jq -c '[.config.name, .config.effort, .config.tier, (.reviewers[] | ([.messages[].effort] | unique), .requestedTier, ([.messages[].servedTier] | unique))]' \
     "$bench/probe"/probe/C1-*/run-1/meta.json
   ```

   For the manager, `agents` writes a tier override too (see Configurations). The requested tier and the served tiers of the manager must equal the tier of `managerConfig`; a manager served at another tier gives no kept recall (see Stages):

   ```bash
   jq -c 'select(.managerConfig) | [.managerConfig.tier, (.manager.agents["manager-1"] | .requestedTier, ([.messages[].servedTier] | unique))]' \
     "$bench/probe"/probe/C1-*/run-1/meta.json
   ```

3. Build the workspace of a split. A `code` case runs as a loop with `C3`, the production loop, a `plan` case with `P1`, a `plan-delta` case with `Pd`, and a `code-delta` case with `Cd`. The current held-out keys are in the repository, so `keys` stays empty; a new held-out set keeps its keys outside the repository (see Cases) and gives their folder with `--keys`.

   ```bash
   split=dev; ws="$bench/$split"; keys=()   # held-out: split=heldout; ws="$bench/heldout"; a new held-out set: keys=(--keys <keys dir>)
   for f in "$skill/cases/$split"/*.json; do
     [[ $f == *.key.json ]] && continue
     case "$(jq -r .kind "$f")" in
       code) arms=(--arms C3 --loop) ;; plan) arms=(--arms P1) ;;
       plan-delta) arms=(--arms Pd) ;; code-delta) arms=(--arms Cd) ;;
     esac
     bun "$skill/scripts/prepare.mjs" case --case "$f" "${arms[@]}" --runs 3 --out "$ws" --project "$project" "${keys[@]}"
   done
   ```

4. Do these steps again until `loop` prints that the loop ends for each run under `"$ws"/*/C3-*/`. A split without a `code` case has no loop run: then do steps 4.1 and 4.2 once.
   1. Dispatch each reviewer prompt that `bun "$skill/scripts/score.mjs" names "$ws"` lists and that has no block yet, and each fixer prompt that it lists, as in step 3 of the procedure. A fixer prompt never gets a block, so `names` lists a fixer prompt only until its `fixer/fixer-1.patch` exists (an empty patch also counts). Do not dispatch a fixer prompt again while its fixer runs, because `transcripts` takes the latest transcript of a name. Line 1 of each prompt names the agent. The omp task tool can need a non-empty context and adds its own text before each task; this is correct, because the task text stays as written. Run at most 8 agents at a time, below the 9 concurrent agents from which omp moves runs to worker threads, and keep the same load for every configuration (see omp compatibility). Save each block in `blocks/<reviewer>.md` of its round folder. A reviewer that hit provider errors and then returned its block is valid. A reviewer that returned no block needs a new dispatch of the same prompt: save the new block over the file of that reviewer. `score.mjs findings` then drops the judge answers of the findings whose text changed, so the judge answers those findings again.
   2. Run `bun "$skill/scripts/score.mjs" findings "$ws"`, then `bun "$skill/scripts/prepare.mjs" manager --ws "$ws"`, and dispatch the manager prompts that `names` lists (see Stages). Run `bun "$skill/scripts/score.mjs" pairs "$ws" --cases "$skill/cases" "${keys[@]}"`. Then dispatch the judge, a model of another family than the reviewers, as `references/judge.md` and step 4 of the procedure tell. A task-tool judge runs on the model of the dispatching session, so run that session on a model of another family, or dispatch the judge through an agent file that sets such a model. After round 1 of a loop, the judge reads the tree of the round in `<ws>/trees/` (see Review loop). When `pairs.json` holds no finding without an answer (for example after a round with no findings), do not dispatch the judge, and go to the next step. `loop` and `report` read a missing `judgments.json` as no answers.
   3. For each loop run that has not ended, run `bun "$skill/scripts/prepare.mjs" loop --run <run dir> --cases "$skill/cases" "${keys[@]}"`. When `loop` writes `round-<r>/fixer/` and stops, dispatch the fixer prompt (`names` lists it until the fixer writes `fixer/fixer-1.patch`) and run `loop` again. When `loop` writes the next round, its prompts are the next prompts to dispatch.
5. After the last dispatch, run `bun "$skill/scripts/score.mjs" transcripts "$ws" --omp-sessions <session folder>`. Give the session folder itself: omp can write the transcripts of a nested dispatch to a subfolder (`<session>/<parent>/<parent>.<name>.jsonl`), and `transcripts` searches the session folder and all its subfolders. `transcripts` stops before it writes when a transcript fails the shape check (see omp compatibility). Run `bun "$skill/scripts/score.mjs" sample "$ws"`, and give `second-sample.json` to a second judge, which writes `judgments-second.json` (see Decisions). Then run `bun "$skill/scripts/score.mjs" report "$ws" "${keys[@]}" --configs <name,...> --reference <production configuration> --margin <m>`, with the configuration names in the column order.
6. Do steps 3 to 5 for the dev split, then once for the held-out split. Apply the decision rule that the plan of the run fixes before any run (see Decisions) to the table `### Decision: heldout` of the held-out `report.md`. A choice of model, effort, or tier compares each configuration with the production setting: give that setting as `--reference`, and read the equivalence row.
7. Append a new entry to `results.md` with the setup, the tables, and the decision. A check run that must not change the repository skips this entry. Then remove the generated agents and the tier overrides with `bun "$skill/scripts/prepare.mjs" clean --project "$project"`, and delete the workspaces and the `baseline-plugin`, `variant-*-plugin`, and `selfreview-*-plugin` folders next to them.

## Decisions

A decision compares a candidate with a fixed baseline on a sample that a power plan sizes. The plan of the run records the rule, the margin, and the sample size before the deciding runs. The audit of plan #133 found that most decisions of the earlier plans had too little power: a neutral candidate passed a 2-per-50 bound in fewer than half of the comparisons, because detection is close to fixed for each defect and only 2 to 4 cases of a comparison differ. Plan #135 replaced the bootstrap rule with the betting test below after its A/A pilot (see `results.md`).

1. Frame and assumption S. The case is the unit of inference, and the run noise is a second level inside each case (Abadie, Athey, Imbens, and Wooldridge, Econometrica 88(1), 2020; Miller, "Adding Error Bars to Evals", arXiv:2411.00640, 2024). The betting test of step 5 needs independent cases with a common mean. The corpus design does not prove that: the held-out cases are frozen, and they come from selected production escapes and from seeded defects (see Cases). So a decision states it as an assumption, not as a fact.
   - Assumption S: the corpus cases are independent draws from the population of review rounds that the case-building procedure of Cases gives.
   - A pass of the betting row claims "not worse on that population, if S holds". Without S, only the fixed-corpus check of step 5 holds: "not worse on these cases". A ship decision rests on S.
   - The corpus cannot test S from inside: a frozen, selected set of cases shows no sign of how it was selected. The decision table names S beside the betting row. It also gives `Seeded cases of the shared cases with known defects` when the case files tell it: code cases use `patch`, and plan cases use the boolean `seeded`. A plan case without that field has unknown seeded status, so a table that includes it gives `-`. Cases lists the two known limits of S: related rounds of one plan and the 12 plans already shared between splits.
2. Measure. For each shared case c with k_c > 0 known defects, e_c is the mean escaped defects over the runs of the candidate minus the mean over the runs of the reference, divided by k_c. So e_c is from -1 to 1, and each run counts: a candidate that finds a defect in half of its runs has e_c = 0.5 there. The decision measure N is 50 times the mean of e_c, "escaped per 50 known, each case weighs 1" (`Escaped per 50 known difference from <reference>, each case weighs 1 (N)`). A case with 14 known defects weighs as much as a case with 1. The pooled escaped defects per 50 known (W) and the bootstrap intervals stay in the report as information and do not decide: a valid bound on W needs a cap on the known defects of a population case, and no cap holds.
3. Neutral-data limit. When no case differs, no valid rule can pass before (1 - m / 50)^n <= 0.05 for n cases with known defects and the margin m: 36 cases at margin 4 and 74 at margin 2. A candidate that loses a whole, fully found case with the chance m / 50 is at the margin, and it shows no difference in n cases with the chance (1 - m / 50)^n. The limit bounds a neutral candidate only: a candidate that is better in enough cases can pass with fewer cases, for example 5 cases with e = -1 at margin 4. The betting test itself passes cases without a difference from 40 cases at margin 4. The report gives `neutral-data limit: <n> of <N> cases with known defects` as information. The limit never stops a decision: the test decides from the data.
4. Power plan and per-reviewer feasibility. Before the deciding runs, run an A/A pilot on the planned corpus at the planned model, effort, and tier: the baseline arm and its control copy `A<arm>` (see Arms) on the same cases, at least 2 of them. Score and judge the pilot, then run `bun "$skill/scripts/score.mjs" power "$ws" [--keys <dir>] [--arms <folder>,<folder>] [--margins <m>,...] [--cases <dir>] [--reviewer <code-reviewer|plan-reviewer>] [--split <dev|heldout>]`. `power` takes the one control copy `A<folder>` and its folder of the valid runs, or the two folders of `--arms`, on the cases that both ran. It prints:
   - W with its standard error over the cases, and N.
   - The neutral-data limit of each margin (default 2 and 4 per 50 known).
   - The cases with known defects per reviewer in the dev and held-out folders of the corpus (`--cases`, default `cases/` of this skill), from the case files and the key files, by count only. With `--keys`, every held-out key comes from the keys folder, as for `pairs` and `report`, so a held-out set whose keys stay outside the repository counts too.
   - The deciding corpus of the simulation: the cases of `--split` (default `heldout`) of `--reviewer` (default the reviewer of the pilot cases; give it when the pilot holds code and plan cases). Only these cases give the known defects of a simulated case.
   - A seeded simulation of the rule: for each margin, the smallest number of cases with known defects at which at least 80% of 1000 neutral paths pass the not-worse betting test, at 1, 2, 3, and 4 runs per case (`> 400` when 400 cases do not reach it). A simulated case draws its known defects from a case of the deciding corpus, and each defect draws its detection rate from the known defects of the pilot, the same rate for both arms. Each path draws 400 cases once, and the sample of n cases is the first n cases of the path (common random numbers). So a path that passes at n also passes at every larger n, the pass share never falls as n grows, and the table gives the first n that reaches 80%.

   Record the table and the chosen cases × runs in the plan. The simulation assumes that new cases have the detection rates of the pilot cases. On 2026-11-17 the corpus held 23 held-out `code-reviewer` cases and 44 held-out `plan-reviewer` cases with known defects. With the code pilot of plan #135, the `code-reviewer` table needed 47 cases at 2 runs and 45 at 4 runs at margin 4, and 96 to 143 cases at margin 2. The `plan-reviewer` table (`--reviewer plan-reviewer`, with the code pilot's detection rates) needed 48 cases at 2 runs and 45 at 4 runs at margin 4, and 96 to 165 at margin 2. So a neutral `code-reviewer` change cannot pass at margin 4 until the corpus grows, because 23 cases are below the neutral-data limit; a clearly better change can still pass. The 44 `plan-reviewer` cases are just below the 80% line at margin 4 even with 4 runs per case. Margin 2 is out of reach for both until the corpus grows (see Cases).
5. Pass rows. With `--margin <m>`, the decision table gives these rows for each column against the reference:
   - `Not worse than <reference> by <m> escaped per 50 known: betting test on N, if assumption S holds`: a one-sided betting test of H0 "mean e >= m / 50" (Waudby-Smith and Ramdas, "Estimating means of bounded random variables by betting", JRSS-B 86(1), 2024). It maps each e to (e + 1) / 2, takes the cases in a seeded order, and bets with predictable plug-in bets that are cut so that one case keeps at least 1 - 0.9 of the capital. The row gives `pass` and stops when the capital reaches 1 / 0.05 = 20, and it gives the capital.
   - `Equivalent to <reference> within <m> escaped per 50 known: two one-sided betting tests on N, if assumption S holds`: `yes` when the test above and the test of H0 "mean e <= -m / 50" both reject, with both capitals.
   - `Not worse than <reference> by <m> on these cases, run noise only: a check, not a ship decision`: the fixed-corpus check. It holds the cases fixed and bootstraps only the runs of each case, and gives `pass` when the upper end of the 90% run interval of N is below m. With one run per case it has no run noise to draw, and its interval is N itself.
   - `Neutral-data limit at <m> per 50 known (information)` (see step 3).
6. Fixed reference. The reference column of a decision is always the named baseline: the baseline arm, or the production setting for a choice of model, effort, or tier. `report` refuses a decision table of two or more columns without `--reference`, and it never picks the column with the fewest escaped defects, because that choice favors noise. A choice of model, effort, or tier uses the equivalence row against the production setting.
7. Margin rules. The plan of the run can fix another rule before the runs. Without one, use these defaults:
   - A mechanism change that does not aim at recall, for example a new check or a new input: not worse by 4 escaped defects per 50 known (`--margin 4`), and the exact tests of step 8 do not show more wrong findings or more unknown ratings at p < 0.05.
   - A change that aims at recall: a superiority test (`--margin 0`), so the betting test must show a mean e below 0. No count of cases without a difference passes it.
8. Exact tests. The decision table gives `Wrong findings / runs` and `Unknown ratings / runs` for each column. Against the reference, it gives the one-sided exact Poisson rate test of more wrong findings and of more unknown ratings, with the valid runs of each column as the exposure: given the sum of the two counts, the count of the column is Binomial(sum, runs of the column / runs of both columns) when the rates are equal. A point check of the counts fails neutral candidates too often, so use the p value.
9. Sequential runs. A decision can run in looks in place of a fixed sample. The procedure has these steps:
   1. Declare the whole comparison once, before any case: `bun "$skill/scripts/prepare.mjs" sequential-plan --cases <case.json,...> --reference <arm>@<config> --candidates <arm>@<config>,... --looks 1,2,3,4 --out "$ws"`. Give every case file of the decision, the reference arm and each candidate arm with its configuration (for example `--reference C3@high --candidates C3@medium,C4@high`), and the runs of the looks (look k has the run k, at most 4 looks). Each entry is one arm folder `<arm>-<config>`, so a choice of model, effort, or tier declares the same arm at two configurations. An A/A control copy `A<reference>` of the batch is a candidate too. It writes `<ws>/run-plan.json` with the reference, the candidates, and one key for every case, declared arm folder, and run of every look, and it refuses a file that exists. Do not edit or remove the file.
   2. `case --sequential` (in place of `--runs`) takes the arms and the configurations of the case from `run-plan.json`, not from its options. Each call prepares one more look in every declared arm folder of the case: the first call builds look 1 with one run per arm folder, and each later call adds one run to each. It refuses `--arms` or `--configs` that differ from the declaration, a case or a look that the file does not declare, arm folders that do not exist or that hold different numbers of runs, and a workspace without the file. It writes no key.
   3. After each look, score and judge the runs and run `report --arms <folders> --reference <reference folder> --margin <m> --sequential`. A workspace with `run-plan.json` is sequential: `report` without `--sequential` refuses it, because the fixed-sample rows at threshold 20 would spend the whole error at one look. The decision table and the sequential looks have the same columns: `--arms` must hold exactly the declared reference folder and every declared candidate folder, in any order, and `--reference` must name the declared reference folder. `report` refuses `--configs` and `--arms` with a missing or an undeclared folder, and names these folders.
   - The capital of the betting test holds at any time only for cases that come one by one. A later look adds runs to the same cases and so changes the earlier e values. So the looks keep the O'Brien-Fleming alpha spending of Lan and DeMets over at most 4 looks: look k runs the betting tests on the per-run means of the runs 1 to k, at the error alpha_k that it spends, with the threshold 1 / alpha_k.
   - For 4 looks and a one-sided error of 0.05, the errors are 0.0000886, 0.00549, 0.0181, and 0.0264, and the thresholds are 11290, 182, 55, and 38. The errors add up to 0.05, so the chance of a false pass over all looks stays at 0.05 or below. Without the spending, looks that stop at the first pass raise the chance that a true loss of 2 per 50 passes from 0.06 to 0.14.
   - With `--sequential`, the sequential looks are the decision. The not-worse row and the equivalence row of the decision table then give `see sequential looks: not-worse decision` and `see sequential looks: equivalence decision`, because their threshold 20 spends the whole error at one look.
   - Each look runs four betting tests at its error alpha_k: not worse (H0 "mean e >= m / 50"), worse (H0 "mean e <= m / 50"), not better (H0 "mean e <= -m / 50"), and better (H0 "mean e >= -m / 50"). The not-worse decision gives `pass` when the not-worse test rejects and `fail` when the worse test rejects. The equivalence decision gives `yes` only when the not-worse and the not-better tests both reject, and `no` when the worse or the better test rejects. Each decision stops on its own rule, and the last look that `run-plan.json` declares gives `no pass` and `no` without a stop. The errors stay those of 4 looks, so a plan of fewer looks spends less than 0.05. A choice of model, effort, or tier reads the equivalence decision.
   - A look decides only when the declared grid is complete up to the look. `report` reads the expected runs from `run-plan.json` only, not from the runs or the folders of the workspace. Every declared key of the look and of the earlier looks, for every case and every compared arm folder, needs a valid run of its case, arm folder, and run number whose configuration is the configuration of the key, and every run of the compared columns up to the look needs a key. So a run that is missing in one arm folder, or a look prepared for some cases only, holds the look. Else the look gives `incomplete look (<reasons>)` and neither passes nor fails. The reasons are `no run-plan.json`, a key without a valid run (for example a missing arm folder or run), `<run> has no configuration`, `<run> has the configuration <x>, not <y>`, and `<run> not in run-plan.json`. A run that is missing or invalid can depend on the case or the reviewer, and then the cases of the look no longer have a common mean. Run the missing runs, or fix the invalid ones, before the look decides.
   - `## Sequential looks` gives each look of each column: the valid runs, the cases with known defects, the error and the threshold of the look, N, the four capitals, the not-worse decision, and the equivalence decision.
10. Batch control. Each batch of deciding runs also runs the control copy `A<arm>` of the baseline arm on a subset of at least 6 of its cases with known defects; a control case without known defects gives the drift test no value. `## Batch drift` gives the escaped difference of each control copy against its arm: the shared cases, the shared cases with known defects, W with its bootstrap interval as information, N, and with `--margin` the capital of the two-sided betting test of H0 "-m / 50 <= mean e <= m / 50". The test uses the hedged capital, the larger half of the two one-sided capitals, and the threshold 20. When the capital reaches 20, the row gives `leaves ±<m>`; such a batch does not decide, so run it again. Else it gives `not shown to leave ±<m>`. Fewer than 6 shared cases with known defects give `too few cases with known defects (<n> of 6)`. Plan #115 measured a drift of 2.64 per 50 known for one arm on the same 8 cases.
11. Second judge. After the first judge, run `bun "$skill/scripts/score.mjs" sample "$ws" [--seed <n>]` on each workspace that decides. It writes `second-sample.json`: every `matches` answer with the verdict `match`, a seeded 10% of the other `matches` answers and of the `adjudications`, every `reargued` answer with the verdict `match`, and a seeded 10% of the other `reargued` answers, each list mixed and without the answers. A found known defect comes only from a `match` answer, so the sample takes each of them. Give the file to a second judge from another model family than the first judge (see `references/judge.md`). The `## Judge agreement` line of `report` also gives the number of the `match` answers that the second judge answered, and the items of the sample that it answered.
   - A report with `--margin` decides, so it needs an answer of the second judge for every item of the sample. `sample` records its seed in `second-sample.json`, and `report` derives the sample again from the current `judgments.json` with that seed (the default seed without the file). So a match that the first judge adds after the sample, for example in a later sequential look, needs an answer too, and an answer to an item that is no longer in the sample does not count. Until each item has an answer, the not-worse row, the equivalence row, and each sequential look give `second judge incomplete (<answered> of <items>)` and no pass. A missing `judgments-second.json` answers no item. After new first-judge answers, run `sample` again and give the new sample to the second judge. A report without `--margin` needs no second judge.

## Procedure

1. Pick the arms and the configurations for the decision (see `results.md`), and use the last docks-kit CLI release (`cli-v*` tag) as the baseline ref. Fix the decision rule, the margin, and the sample size of the power plan in the plan of the run before the deciding runs (see Decisions). Run every arm at least twice, or in sequential looks. Put dev cases and held-out cases in separate workspaces, so that the dev `pairs.json` holds no held-out text.
2. Build the agents and the workspaces. Keep workspaces outside the working tree, because each snapshot is a full repository copy. Do not use a path that contains the words benchmark or judge, because the prompts name it and `prepare.mjs` refuses it.

   ```bash
   repo="$(git rev-parse --show-toplevel)"
   skill="$repo/.agents/skills/review-benchmark"
   bench="$(git rev-parse --path-format=absolute --git-path docks-review)/bench-<label>"
   ref="$(git describe --tags --match 'cli-v*' --abbrev=0 origin/main)"
   bun "$skill/scripts/prepare.mjs" agents --baseline-ref "$ref" --model openai-codex/gpt-6.1-sol \
     --efforts low,medium,high,xhigh --tiers priority,default --out "$bench/dev"
   bun "$skill/scripts/prepare.mjs" probe --out "$bench/probe"
   for c in code-96-r1 code-89; do
     bun "$skill/scripts/prepare.mjs" case --case "$skill/cases/dev/$c.json" --arms B0,C1,C3 --runs 2 --out "$bench/dev"
   done
   bun "$skill/scripts/score.mjs" names "$bench/dev"
   ```

   Dispatch and check the probe (see Probe) before the cases. `prepare.mjs` stops with a message when a commit is missing or a patch does not apply. When a case commit is missing and the case has `pull`, and `refs/review-bench/pull/<n>` does not exist, `case` fetches the head of the pull request once into that ref and never moves the ref. When `refs/review-bench/pull/<n>` exists, `case` does not fetch again. A commit that the repository holds needs no fetch, whatever holds it, for example a local branch. When a case commit is still missing, or the fetch fails, `case` stops before it writes the workspace; a case without `pull` stops in the same way when a case commit is missing. The message names the case field, its missing commit, and the recovery command `bun "$skill/scripts/prepare.mjs" pin --case <case file>`; the message of a failed fetch also gives the git error. The message gives the full paths in POSIX single quotes, so the command runs in a shell as printed. `pin` needs `pull` in the case. It fetches the head of the pull request with `--no-tags --no-write-fetch-head` into a temporary ref `refs/review-bench/incoming/<n>-<process id>-<8 random hex characters>`, which only this run writes, and reads the commit of that ref once. It pins each case commit (`base`, `head`, `delta_base`, `repo_ref`) that this head reaches and that `origin/main` does not reach at `refs/review-bench/kept/<full sha>`. It creates a pin only when the pin does not exist; an existing pin of the same commit is correct, so a second run of `pin` moves no ref. Then `pin` deletes the temporary ref. `pin` never writes `refs/review-bench/pull/<n>`. When the fetch fails, `pin` exits with the git error and leaves no temporary ref. When a pin fails, `pin` exits with the git error and keeps the temporary ref, which the message names; delete that ref with `git update-ref -d <ref>` after a run of `pin` succeeds. When the head does not reach a case commit that `origin/main` does not reach, `pin` writes no ref and exits with the commit named; then correct `pull`. `case` and `pin` fetch from `origin`: when `origin` is a fork, set `origin` to the remote of DocksDocks/docks-kit. After `pin`, run `case` again: it finds the commit present and pinned. Before it writes the workspace, `case` pins each case commit that `origin/main` does not reach at `refs/review-bench/kept/<full sha>`, because `git gc` can remove a commit that no ref reaches; an existing pin stays as it is. `loop` then finds the commit through the pin. To remove a pin that no case needs, run `git update-ref -d refs/review-bench/kept/<sha>`. For loop runs, add `--loop` to `case` and follow Review loop.

   To compare a candidate that also changes the plan contract, give its variant to `agents --contract-overlay` (see Arms). `agents` removes the agents of its earlier call, so give it every variant that you still run. To add arms to case folders that a workspace already holds, run `case` again with only the new arms and `--extend`. `--extend` keeps each arm folder that exists, so a variant that already ran there needs a new name, for example `ao` for candidate A with its contract change. Before you dispatch the new runs, check that the `meta.json` of each run of the variant records the `contractOverlay` that you expect. After the runs, check in their transcripts that each reviewer read the copy `plan-contract.md` of its run:

   ```bash
   bun "$skill/scripts/prepare.mjs" agents --baseline-ref "$ref" --model <model> --efforts <list> --tiers <list> \
     --variants a=<ref of candidate A>,ao=<ref of candidate A> --contract-overlay ao --out "$bench/heldout"
   bun "$skill/scripts/prepare.mjs" case --case "$skill/cases/heldout/<id>.json" --arms Vao --runs 5 \
     --out "$bench/heldout" --extend
   jq -r '.contractOverlay' "$bench/heldout"/<id>/Vao-*/run-*/meta.json
   ```
3. Dispatch from an omp session that runs in the `--project` folder of `agents`. One message holds every prompt of one arm folder and run, one subagent per prompt file, and at most 8 subagents run at a time (see omp compatibility): the agent is the name on the first line, the task is the text after the empty line, and the task name is the one that `score.mjs names` prints for that file. Do not set the `effort` field of a task: with `task.enableEffort`, it replaces the `thinking-level` of the agent, so `agents` stops when `task.enableEffort` is `true`. The task name drops separators and case, so `names` and `transcripts` stop when two prompts get the same name (for example cases `code-7` and `code_7`); rename one case. Alternate the arms and the configurations from message to message. Load changes round time, so keep the same load for every arm. Save each returned block as plain Markdown in `blocks/<reviewer>.md`; `score.mjs` also unwraps JSON-wrapped output from runtimes that return structured text. Fill `meta.json` with `score.mjs transcripts <ws> --omp-sessions <session folder>`. `transcripts` finds the transcript of each prompt by its task name: `<name>.jsonl`, `<parent>.<name>.jsonl` for a nested task, or `<name>-<n>.jsonl` for a repeated name. Two workspaces that one session dispatches can use the same task names, so `transcripts` keeps only the transcripts whose first user message (the task) names a path under the case folder of the prompt in `<ws>`. Each prompt of `prepare.mjs` names such a path. Of these transcripts, `transcripts` takes the latest repeat, and it runs the shape check of `scripts/omp.mjs` on it before it writes any `meta.json` (see omp compatibility). When no transcript of a prompt names such a path, `transcripts` gives the task name of the prompt as missing. The prompts hold absolute paths, so `<ws>` must give the same absolute path as the `--out` folder of `prepare.mjs`; a path through a symbolic link does not match. A run with a `config` needs the transcript facts of each reviewer, so write seconds and tokens by hand only for a run without `config`. For another runtime than omp, write the same fields from its transcripts.
4. Score and judge:

   ```bash
   bun "$skill/scripts/score.mjs" findings "$bench/dev"
   bun "$skill/scripts/prepare.mjs" manager --ws "$bench/dev"   # then dispatch the manager prompts (see Stages)
   bun "$skill/scripts/score.mjs" pairs "$bench/dev" --cases "$skill/cases"
   # dispatch the first judge (see below) and wait until it has written judgments.json
   bun "$skill/scripts/score.mjs" sample "$bench/dev"   # then dispatch the second judge and wait for judgments-second.json (see Decisions)
   bun "$skill/scripts/score.mjs" transcripts "$bench/dev" --omp-sessions <session folder>   # again, for the manager transcripts
   bun "$skill/scripts/score.mjs" report "$bench/dev" --configs <name,...> --reference <baseline column> --margin <m>
   ```

   For held-out cases, add `--keys <dir>` to `pairs` and `report` (see Cases). `--configs <name,...>` of `report` sets the columns of the configuration tables and their order; the default is the configuration names in run order, without the control copies `A<arm>`. `--arms <folder,...>` compares arm folders in place of configurations; give `--configs` or `--arms`, not both. `--reference <column>` names the reference column: a folder of `--arms`, or a configuration. A decision table of two or more columns needs it (see Decisions). For example, `--arms V16-xhigh,V17-xhigh,Va-xhigh --reference V17-xhigh` compares each variant with the current prompt. `--margin <m>` adds the margin rows and the drift check, and `--sequential` (with `--reference` and `--margin`) adds the sequential looks. `--lead <folder,...>` with `--lead-ref <folder>` adds the self-review lead. These options are described below.

   `findings` parses the blocks into `findings.json`. A finding id names the place of the finding (the case, arm, run, round, reviewer, and position in the block), not its text. So before it writes, `findings` compares each finding with the previous `findings.json`. When the text of an id changed (its severity, category, locator, or text) or the id is gone, for example after a reviewer was dispatched again, `findings` removes the answers of that id from `judgments.json` and `judgments-second.json` and prints the ids. Then the judge answers these findings again.

   Between `pairs` and `report`, dispatch one judge agent from another model family than the reviewers. Give it `references/judge.md`, the workspace path, and the cases path (and the keys folder, with `--keys`). The judge reads `pairs.json`, the key files, and the snapshots, and writes `judgments.json` with an answer for every candidate pair in `pairs.json`, a `reargued` answer for every protected pair (a finding and a protected decision of its case, see Cases), and a rating for every finding without a `match` answer for a known defect. `report` stops and names the pairs and the protected pairs that have no answer and the findings that have neither a `match` answer nor a rating. When no pair and no finding needs an answer (for example when the reviewers returned no findings), do not dispatch the judge: `loop` and `report` read a missing `judgments.json` as no answers. The judge does not read `findings.json` or the arm folders, because they name the arms.

   Then check the judge with a second judge. Run `bun "$skill/scripts/score.mjs" sample "$bench/dev"`, and give `second-sample.json` to a second judge from another model family than the first judge (see Decisions). It follows the Second judge section of `references/judge.md` and writes `judgments-second.json`. When that file exists, `report` compares each of its answers with the same answer of `judgments.json` and gives the agreement rate and the number of the `match` answers that it answered under Judge agreement. It stops when the second judge answers a pair, a protected pair, or a finding that `judgments.json` does not answer.

   `report.md` has one summary row for each case and arm and one row for each run. The summary gives the mean, median, minimum, and maximum of recall; the mean of valid extras, wrong, unknown, unresolved, unknown pairs, and re-argued decisions per run; the mean read coverage of the reviewers; and the median, minimum, and maximum of seconds and tokens. Valid extras, wrong, unknown, and unjudged count the findings that match no known defect, by their adjudication rating. Unknown pairs counts every `unknown` answer of the judge for a pair of a finding of the run and a known defect. Such an answer can hide a missed match, or a valid extra that only repeats a found defect. Unresolved is the subset that can change recall: the known defects that the run did not find, where the judge answered `unknown` for a pair of the defect with a finding of the run. In a dev workspace, read the `unknown` pairs in `judgments.json` before the decision. Re-argued, in the Runs table, lists the protected decisions of the case that a finding of the run re-argues: the judge answered `match` for their protected pair (see the Decision pass of `references/judge.md`). A protected decision is no known defect, so it counts in neither known nor recall, and a finding that re-argues one keeps its own answers and rating; a reargued `unknown` counts nowhere. The summary gives the mean count of these decisions per run. Diff read, in the Runs table, is the lowest `diffCoverage` (see Workspace) of the reviewers of all rounds of the run, also of an invalid run, so it shows the reviewer that read the least of its own diff. `Diff read mean`, in the summary, is the mean of the `diffCoverage` values of the reviewers of all rounds of the valid runs, so a run counts with each of its reviewers. The decision table of each configuration or arm section (see below) gives the same mean for each column, over the valid runs of the column. A reviewer without the field gives no value, and these cells give `-` without a value. Read coverage is an observation: it decides nothing and makes no run invalid. A run of several rounds adds the seconds and tokens of its rounds, and its recall and finding counts cover every round.

   `report` checks each run that has a `config` against the transcript facts of each reviewer. It also checks the fixer of each round of such a loop against the fixer setting `fixerConfig` in the same way. The run is invalid when an assistant message comes from another model (for example after a usage fallback), when a message of the configured model ran at another effort (the effort that was active at the message; an effort change before the first assistant message is setup), when a message of the configured model shows another served tier (only for a configuration with a tier), when an agent has no transcript facts or no served assistant message, when a loop round gave findings to the fixer (`fix.extras` or `fixedByFixer`) but has no fixer entry (`round-<r>/fixer-1: no transcript facts`, for example after `loop --fixer-patch`), or when a loop has a fixer entry but no `fixerConfig`. A failed request (an assistant message with `stopReason` `error` and no served tier) stays out of the model and served-tier checks, but its time counts in the seconds. The reason of a fixer names its round, for example `round-2/fixer-1: model <model>, not <fixer model>`. Every run, also a run without a `config`, is invalid when a reviewer read outside its inputs (see Read scope); the reason is `<reviewer>: read outside its inputs:` and the first three outside targets. Every run, also a run without a `config`, is invalid when the transcript of a reviewer or of a fixer shows a revived agent (`revived`, see Workspace); the reason is `round-<r>/<reviewer>: revived agent` (`<reviewer>: revived agent` for a run without round folders), or `round-<r>/fixer-1: revived agent`. Every run is also invalid when a round has a reviewer block that holds no review: the block is missing, has no verdict line (`unreadable`, for example a JSON object with only an `acknowledgment` field), or has the verdict `blocked`. Such a run does not show the review of its arm, and a loop must not continue after such a round (see step 4 of Review loop). The reason is `round-<r>/<reviewer>: no review (<verdict>)`, or `<reviewer>: no review (<verdict>)` for a run without round folders, with the verdict `missing`, `unreadable`, or `blocked` of `findings.json`. The Runs table keeps invalid runs; `## Invalid runs` names them with their reasons, and the summary, the configuration or arm tables, and the self-review lead leave them out. Before it writes, `report` stops when the runs of the workspace name more than one omp version (see omp compatibility).

   `## Configurations: <split>` gives one section per case group (`dev`, `heldout`), from the valid runs that have a `config`. Each table of a section has one column per configuration. A loop run is a run with `round-<r>` folders (a `code` case built with `case --loop`, see Review loop). Each other run is a single review, for example of a `plan`, `plan-delta`, or `code-delta` case. A section has these tables, and it leaves out a table that has no runs:

   - `### Decision: <split>` covers all runs of the case group, loops and single reviews together. It gives the runs, the known defects found and escaped per run, the escaped defects per 50 known defects, the mean read coverage of the reviewers (`Diff read mean`), the model, effort, and served tier from the transcripts, `Wrong findings / runs`, `Unknown ratings / runs`, and `Reads of missing paths` (see Read scope). The rows after them compare each column with the reference column: with `--arms`, `Cases shared with <reference>`; the 90% two-level paired bootstrap interval of the difference from the reference column, over the cases that both columns ran, for round 1 recall, escaped defects per 50 known defects, and loop seconds, as information; `Cases with an escaped difference from <reference>`; the two exact Poisson rows; the shared cases with known defects, the seeded share of them, and N; and with `--margin`, the betting row, the equivalence row, the fixed-corpus check, and the neutral-data limit (see Decisions). The loop seconds row compares loop runs only. The reference column is the column that `--reference` names. The bootstrap and the case order of the betting test use fixed seeds, so a rerun gives the same values.
   - `### Code loops: <split>` covers the loop runs. It gives the runs; the model, effort, and served tier from the transcripts, as the decision table; for each round index, the median, minimum, and maximum round seconds, the mode counts, and the known defects found per loop that reached the round; the rounds per loop; the loop seconds (the sum of the round seconds); the known defects found and escaped, the valid extra findings, the extra-only rounds, and the wrong, unjudged, and unknown answers per run; the tokens and side-call tokens; the loops with a fixer and their fixer seconds and fixer tokens; and the known defects found per loop minute.
   - `### Single reviews: <split>` covers the other runs. It gives the runs, the model, effort, and served tier from the transcripts, the median, minimum, and maximum seconds, the known defects found and escaped, the valid extra findings, and the wrong, unjudged, and unknown answers per run, and the tokens.

   `--arms <folder,...>` compares arm folders at one configuration or more, for example `--arms C1-xhigh-fast,B0-xhigh-fast` or `--arms C1-xhigh-fast,C3-xhigh-fast,S1-xhigh-fast,S3-xhigh-fast`. `report` then writes one `## Arms: <split>` section per case group in place of `## Configurations: <split>`. The sections have the same tables from the valid runs of these arm folders, with one column per arm folder in the order of the list. The reference column is the folder that `--reference` names in each case group, and the report text names it. The arm folders can hold different cases, for example when an arm ran only part of the cases. So the decision table also gives `Cases`, the cases of each column, and `Cases shared with <reference>`, the cases that the column and the reference column both ran. The interval rows pair only these shared cases.

   `--lead <folder,...> --lead-ref <folder>` adds `## Self-review lead`, which measures the self-review arms (`S1` and `S3`, see Arms) against a reviewer arm, for example `--lead S1-xhigh-fast,S3-xhigh-fast --lead-ref C3-xhigh-fast`. Give the two options together. The reference can be a loop arm folder, such as `C3-xhigh-fast` built with `case --loop` (the production code-review loop), or a single-round arm folder, such as `C1-xhigh-fast` built without `--loop`. The section has one table `### Self-review lead: <split>` per case group, from the valid runs. The table has one column per lead folder, then a column for the reference folder. Each run counts with its round 1 only: a single-round run is one round, and a loop counts only its first round. These are the rows:

   | Row | Content |
   |---|---|
   | `Runs`, `Cases` | the valid runs and their cases |
   | `Round 1 seconds median`, `min`, `max` | the round 1 seconds of the runs. A round takes the time of its slowest reviewer, so a run of a split arm such as `S3` takes the time of its slowest reviewer |
   | `Known found in a run` | the known defects that round 1 of at least one run found, as `<case>: <ids>` |
   | `Known found that no <reference> run found` | for each case that the reference ran, the known defects that the column found and round 1 of no reference run found: the defects that only this column found. The reference column gets `-` |
   | `Cases without a <reference> run` | the cases of the column that the reference did not run. The row above leaves out these cases |
5. Apply the decision rule in `results.md` to `report.md`. For a losing candidate, read the transcripts of its misses before the next dev iteration.
6. After the dev iterations, prepare and run the held-out cases once in their own workspace, under the constraint above.
7. Append the result tables, the commit, the baseline ref, the configurations, and the decision to `results.md`.
8. Turn each defect that escaped review into a new case (see Cases).
9. Remove the agent files (also the fixer and manager agents), the list of configurations, and the tier overrides with `bun "$skill/scripts/prepare.mjs" clean` (with the same `--project` as `agents`). Then delete the workspaces and the `baseline-plugin`, `variant-*-plugin`, and `selfreview-*-plugin` folders next to them.

## Outcomes

`bun "$skill/scripts/outcomes.mjs" --repo <owner/repo> [--json]` measures each landed plan after merge. It needs `gh` with read access. It lists each closed plan issue (label `plan`) with its landing pull request: the last merged pull request that closed the issue. For each plan it counts:

- reverts: merged pull requests and commits of the default branch whose title, body, or message holds the word revert and names the merge commit (7 or more hex characters) or the number of a landing pull request. An open pull request, or one that closed without a merge, reverts nothing, so it does not count;
- follow-up defects: issues and pull requests, created after the landing merge, that cite a landing pull request or the plan (`#<n>`, `<owner/repo>#<n>`, or its GitHub URL), are no revert, and are no plan work: no plan issue (a closed plan, or an open issue with the `plan` label) and no pull request that closed a plan. Each has a label with bug, fix, or regression, a title with fix, bug, regression, hotfix, or broken, or the `Unreached:` marker of the follow-up issue of unreached LOW findings (`plan-contract.md`, Round ceiling);
- unreached issues: the issues with that marker that cite a landing pull request or the plan, also when they are plan work, which the follow-up defects leave out.

The table has one row per plan, and `--json` prints the rows with the id of each counted item. The counts are a heuristic, so read the listed items before you use a count: for example to choose control cases, or to judge after merge whether the rows of a `REVIEW.md` lower the follow-up defects.

## Ablation

Ablation tests whether a rule group of a reviewer prompt still earns its place, as the review-rule pruning routine asks. A rule group is one checklist block, one lens section, or one group of triggered-check rows.

1. Make a candidate that removes one rule group from the full prompt and changes nothing else.
2. Run the candidate against the full prompt, dev cases first, then the held-out cases once. For `code-reviewer`, give the full prompt as `--baseline-ref` and compare `B3` with `C3`. For `plan-reviewer`, give both prompts as `--variants`. For the docks `code-review` skill, give both skill roots as `--self-review-roots` and compare the `S3<root>` arms.
3. Apply to the held-out report the not-worse decision rule that the plan of the run fixes before any run. Do not take the bounds from this file. When the plan fixes no rule, use the default margin rule of a mechanism change (see Decisions): not worse by 4 per 50 known, with the exact tests of the wrong findings and the unknown ratings.
4. Keep the removal only when the rule holds and the user approves it. Ask the user, and record the answer, the tables, and the decision in `results.md`.
5. When the rule does not hold, keep the rule group, and record the result in `results.md`.

## Tests

The vitest project `review-benchmark` runs the suite in `tests/`: one test file per area of the scripts, with the shared helpers in `tests/helpers.mjs`. `bun run check` runs it with the other projects; to run only this suite:

```bash
bunx vitest run --project review-benchmark
```

The project runs on Linux only, because the suite runs `sh`, `ps`, GNU tar, `gpg`, and `gpgconf`, and `keys.mjs` needs GNU tar (`--sort=name`, `--to-command`), which the BSD tar of macOS does not have; one test needs the util-linux `script` command and is skipped where `script --version` does not print `util-linux`. The suite needs git and a clone with the full history of the repository and `refs/remotes/origin/main`, because the cases name old commits; so the CI jobs that run it check out with `fetch-depth: 0`. The suite needs no network. A test that copies the scripts to a scratch repository also gives the copy the `cli/src` folder and the `SoT/toolchain.json` pins of this checkout, because the scripts import them. The preflight tests put a fake `omp` first on `PATH`, so no test runs a model. The fixture tests read the redacted omp transcripts of `tests/fixtures/omp/` (see omp compatibility, Fixtures).
